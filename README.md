# WELLKNEWS

숏폼으로 소식을 전하는 뉴스 채널 WELLKNEWS의 공식 사이트이자, 여기서 갈라져 나온
개인 프로젝트들이 사는 도메인.

```
wellknews.github.io
│
├── /          WELLKNEWS   입구
├── /;         SEMICOLON   첫 번째 가지
└── /mamaboy   MAMABOY     두 번째 가지
```

세 공간은 같은 저장소에서 빌드되지만 서로 다른 문서다. 색·타이포그래피·모션·폰트까지
공유하는 것이 없고, 방문자는 자기가 들어간 쪽의 자산만 내려받는다.

## 실행

```bash
npm install
npm run dev
```

| 스크립트          | 설명                                     |
| ----------------- | ---------------------------------------- |
| `npm run dev`     | 개발 서버                                |
| `npm run build`   | 배포용 빌드 (`dist/`)                    |
| `npm run preview` | 빌드 결과 미리보기                       |
| `npm run check`   | 포맷 · 린트 · 타입 검사 일괄 실행        |
| `npm run audit`   | 실제 화면을 열어서 하는 검사 (아래 참조) |
| `npm run format`  | 코드 포맷 적용                           |
| `npm run assets`  | 세 브랜드의 로고·아이콘·OG 카드 재생성   |
| `npm run feed`    | MAMABOY의 RSS 수집·번역 파이프라인 실행  |

## 구조

```
index.html          입구 문서
;/index.html        세미콜론 문서 — 디렉터리 이름이 곧 주소다
mamaboy/index.html  마마보이 문서
src/
  content/site.ts     입구의 모든 카피와 링크
  styles/             tokens → reset → global 순으로 적용
  components/         컴포넌트 + 같은 이름의 CSS Module
  hooks/              스크롤·포인터 관련 동작
  semicolon/          /; 아래의 모든 것 (아래 참고)
  mamaboy/            /mamaboy 아래의 모든 것 (아래 참고)
scripts/            이미지 자산 생성 (원본이 바뀔 때만 수동 실행)
                    세 브랜드의 파생 자산을 함께 생성
scripts/mamaboy/    MAMABOY의 RSS 수집 파이프라인 (Actions가 주기적으로 실행)
assets/             canonical 로고·OG 배경 원본 (배포되지 않음)
public/media/       WELLKNEWS·SEMICOLON용 최적화 이미지
public/mamaboy/     MAMABOY의 추상 색면 (예시 데이터가 쓰는 이미지)
```

입구의 문구를 고칠 일은 대부분 `src/content/site.ts` 한 파일에서 끝난다.

## 이미지 자산

- `assets/logo.svg`가 로고의 단일 원본이다. 화면용 SVG와 PNG, 파비콘, Apple 아이콘은
  `npm run assets`로 생성한다.
- `assets/og-background-v2.webp`는 OG 카드의 배경판이며 로고와 문구는 생성 스크립트가 정확히
  합성한다. 카피는 프로젝트에 설치된 Pretendard와 Instrument Serif 파일로 직접
  래스터화하므로 운영체제의 대체 글꼴에 영향을 받지 않는다.
- `public/media/`의 404, Hero, REPORT, CHANNELS, ABOUT 이미지는 생성형 이미지로 만든
  추상 편집 자산이다. 실제 인물·사건·문서 또는 보도 사진을 나타내지 않는다.
  `hero-newsroom-mobile.webp`는 Hero 원본의 전용 모바일 크롭이다. 생성 프롬프트와
  제약은 `assets/IMAGEGEN.md`에 기록한다.
- `public/media/session/`은 각 SESSION의 실제 기록 사진이다. 분위기를 만들려고
  생성한 그림은 여기 두지 않는다 — «SESSION의 이미지는 장식이 아니라 증거다».
  제작 과정에 실제로 쓰인 시안은 예외가 아니라 그 사건의 기록이므로 그대로 쓴다.
- `public/mamaboy/plate-*.webp`는 사진이 아니라 sharp로 합성한 추상 색면이다.
  크림 종이 위에 젤이 번지고 그 위를 빛이 한 번 스치는, MAMABOY의 소재 그 자체다. 예시
  데이터의 대표 이미지 자리에만 쓰이고, 실제 RSS가 붙으면 각 매체의 이미지가 그 자리를
  가져간다. 무엇을 찍은 것처럼 보이면 안 되므로 인물·제품·장소를 담지 않는다.
- MAMABOY의 파비콘·터치 아이콘·공유 카드(`mamaboy.svg`, `mamaboy-touch.png`,
  `mamaboy-og.png`)는 레터링의 경로에서 직접 만든다. 배경으로 쓰는 생성 이미지가 없다 —
  이 브랜드의 표면은 색면과 반사광이고, 그것은 스크립트가 그대로 합성할 수 있다.
- `semicolon-interval-cool.webp`는 더 이상 SEMICOLON의 인터페이스에 등장하지 않는다.
  `npm run assets`가 공유 카드(`semicolon-og-cool.png`)를 합성할 때 쓰는 배경판으로만
  남아 있고, 파생 크롭인 `semicolon-interval-cool-mobile.webp`는 아카이브 자산이다.
  «Generated imagery may support SEMICOLON. It must never define SEMICOLON.» —
  링크를 공유했을 때 보이는 그림까지 없앨 이유는 없지만, 그 그림이 이 공간이
  무엇인지 정하지는 않는다. 이유는 아래 «디자인 규칙 — SEMICOLON»에 적어 두었다.

## 디자인 규칙 — WELLKNEWS

이 사이트는 아래 규칙을 지키는 것을 전제로 만들어졌다. 요소를 추가하기 전에 확인할 것.

1. **생성 이미지는 브랜드 판면이지 보도 증거가 아니다.**
   인물·실제 사건·식별 가능한 장소·읽을 수 있는 문서·가짜 SNS 화면을 만들지 않는다.
   로고와 모든 문구는 이미지에 굽지 않고 HTML 또는 canonical SVG로 올린다.

2. **검정과 종이색의 대비로 섹션의 역할을 구분한다.**
   Hero·CHANNELS·ELSEWHERE는 야간 뉴스룸, REPORT·ABOUT은 편집 지면으로 읽힌다.
   둥근 카드와 장식적 그림자 대신 이미지 크롭, 괘선, 타이포그래피로 깊이를 만든다.

3. **모션의 이동 거리는 짧게 유지한다.**
   리빌은 10px대만 움직이고 나머지 인상은 불투명도와 타이밍이 만든다.
   거리를 키우면 곧바로 슬라이드쇼처럼 읽힌다.

4. **채널 프리뷰는 플랫폼을 흉내 내지 않는다.**
   CHANNELS의 신호 아틀라스는 배포 방식만 추상적으로 암시한다. 실제 게시물이나 플랫폼
   UI가 확보되기 전까지 생성 이미지를 콘텐츠 썸네일처럼 보이게 사용하지 않는다.

5. **모바일은 별도의 구도로 설계한다.**
   Hero는 전용 세로 크롭을 사용하고, hover 기반 CHANNELS 프리뷰는 전체 아틀라스로
   바뀐다. 모든 링크는 44px 터치 영역과 명확한 키보드 포커스를 유지한다.

6. **모든 모션은 `prefers-reduced-motion`을 존중한다.**
   토큰(`--dur-*`)이 일괄 0으로 떨어지고, 각 컴포넌트도 애니메이션 없는 경로를 갖는다.

7. **하위 프로젝트는 ELSEWHERE 목록으로만 소개한다.**
   특정 프로젝트를 위한 섹션을 만들지 않는다. 새 프로젝트가 생기면
   `site.elsewhere.items`에 한 줄을 더할 뿐이다. 목적지의 디자인을 미리 끌어오지도
   않는다 — 문을 통과하기 전까지는 끝까지 WELLKNEWS의 언어를 쓴다.

8. **상단 메뉴는 세 칸이 상한이다.**
   라벨이 12px·0.16em 대문자라 320px 화면에서 네 번째 항목부터 가로 폭을 넘긴다.
   ELSEWHERE가 메뉴에 없는 이유다.

## SEMICOLON (`/;`)

바쁜 삶을 끝내지 않고 잠시 구분하는 기호. 경계를 가진 경험을 하나씩 떼어내 분석하고,
그 사이 이어지는 생각을 남기는 공간이다.

**«설명하지 않는다. 반응하게 한다.»**

이 공간은 설명해서 이해시키지 않는다. 첫 화면에는 슬로건도 소개문도 정물 사진도 없다.
종이색 공간과 아주 희미한 민트·핑크, 그리고 `;` 하나가 있고, 사람이 움직이면 그것들이
반응한다. 색이 밀려나고, 선이 갈라지고, 한쪽 점은 벽에 부딪혀 멈추고 다른 쪽 점들은
판을 넘어 흘러 나간다. 아무 문장도 읽지 않은 채로 이 공간의 성격을 어느 정도 알게 되는
것이 목표다 — 멈추지만 끝나지 않는 곳.

### 디자인 계보

| 세대 | 이름                                | 무엇이 의미를 옮겼나       |
| ---- | ----------------------------------- | -------------------------- |
| 1    | Editorial Minimalism                | 활자와 여백                |
| 2    | Symbolic Interactive Minimalism     | 기호와 선, 그리고 동작     |
| —    | Image-led Editorial                 | 생성 이미지 (되돌림)       |
| 3    | **Interactive Gradient Minimalism** | 색·공간·기호가 사람에 반응 |

3세대는 새로 시작한 것이 아니라 2세대에서 끊겼던 진화를 이어간 것이다. 이미지 중심
방향을 되돌린 이유는 이미지의 품질 때문이 아니라, Hero에 정물을 놓는 순간 사람이 `;`보다
그림을 먼저 해석하게 되기 때문이다. 그러면 이 공간은 스스로 의미를 전달하는 인터페이스가
아니라 그림의 뜻을 사용자가 풀어야 하는 웹사이트가 된다.

원칙은 한 줄이다 — **콘텐츠에는 이미지가 존재할 수 있지만, 인터페이스는 이미지를 필요로
하지 않는다.** 실제 SESSION의 사진은 그 글 안에서 얼마든지 쓴다.

```
src/semicolon/
  content/site.ts       이 공간의 모든 카피
  content/types.ts      Session · Thread · Meta 타입
  content/sessions.ts   세션 목록 (등록하는 곳)
  content/sessions/     세션 본문 — _template.tsx를 복사해서 쓴다
  content/threads.tsx   스레드 본문과 목록
  motion/               감쇠 함수와 프레임 루프 — 이 공간의 모션 엔진
  styles/               tokens → (공용 reset) → global
  components/           컴포넌트 + 같은 이름의 CSS Module
  pages/                라우트별 화면
  router.tsx            경로 해석 · Link · 깊은 주소 복원
```

### 콘텐츠 체계

|           | SESSION     | THREAD           |
| --------- | ----------- | ---------------- |
| 대상      | 경험한 것   | 생각하고 있는 것 |
| 상태      | 경계가 있다 | 이어지는 중이다  |
| 성격      | 분석        | 단상             |
| 필수 정보 | title       | date             |

길이는 기준이 아니다. 긴 Thread도, 짧은 Session도 있을 수 있다.

### 콘텐츠 추가

CMS나 에디터를 두지 않고 직접 하드코딩한다. 임시방편이 아니라 지금 이 공간의 성격에
맞는 방식이다 — 어떤 세션은 사진이 중심이고 어떤 세션은 문장이 중심이라, 하나의
템플릿에 억지로 맞추는 순간 분석하려던 것을 잃는다.

- **SESSION** — `src/semicolon/content/sessions/_template.tsx`를 복사해 파일을 만들고,
  `content/sessions.ts`의 배열 맨 앞에 등록한다.

  `display`로 그 경험이 지면을 어떻게 쓸지 고른다. 기본은 `column`이다.

  | display  | 자리                                                                |
  | -------- | ------------------------------------------------------------------- |
  | `column` | 제목·메타데이터·본문이 정해진 판면에 앉는다. 대부분의 기록이 여기다 |
  | `stage`  | 본문이 판면 전체를 가져간다. 형태 자체가 내용의 일부일 때만         |

  `stage`를 남발하면 SESSION마다 다른 사이트가 되고 공통 문법이 사라진다.
  «이 경험은 다른 배치로는 전할 수 없는가»에 답할 수 있을 때만 쓴다.
  일반 기록이 대부분이고 특수한 배치는 드물어야 한다.

  `compact`에는 작은 판면(≤599px)을 위한 다른 배치를 적을 수 있다. 문장은
  그대로 두고 장면만 합치는 자리다 — 자세한 이유는 아래 «디자인 규칙 —
  작은 판면»에 있다. 적지 않으면 좁은 화면도 `body`를 그대로 쓴다.

  `cover`는 목록과 본문 머리가 함께 쓰는 한 장이다. 완성품 사진일 필요는 없다 —
  그 경험이 시작될 때의 상태가 더 정확할 때가 많다. `focus`는 그 이미지에서
  의미가 있는 자리(0..1)로, 연출값이 아니라 이미지에 대한 사실이라 데이터 쪽에 적는다.

  배경이 투명한 시안은 그대로 얹으면 판면 뒤의 색면이 피사체 주위로 비쳐 보인다.
  흰 배경을 가진 파일을 써야 한다면 흰 사각형이 생기므로, 그때 배경을 지우거나
  종이색과 섞는 방법을 그 자리에서 만든다.

- **THREAD** — `src/semicolon/content/threads.tsx` 배열 맨 앞에 항목을 추가한다.
  제목은 없어도 되고, 한 문장이어도 된다.

  `form`으로 그 글이 지면 어디에 앉을지 고른다. 길이가 형태를 정하지는 않는다.

  | form          | 자리                                            |
  | ------------- | ----------------------------------------------- |
  | `note` (기본) | 날짜가 여백 칼럼에 앉고 본문이 그 옆에 온다     |
  | `loud`        | 판면 전체를 쓰고 크게 앉는다. 한 문장짜리 생각  |
  | `aside`       | 오른쪽 안쪽으로 물러나 좁고 낮게 앉는다. 곁가지 |

본문은 `<Prose>` 안의 평범한 JSX다. `p`, `h3`, `blockquote`, `figure`가 공통 리듬을
갖고, 그 밖의 구조는 콘텐츠마다 새로 짜도 된다. 크기·행간·폭은 `--prose-size`,
`--prose-leading`, `--prose-measure`를 바깥에서 정해 바꿀 수 있다 — 어떤 생각은
한 문장이라 크게 앉아야 하고, 어떤 글은 좁게 물러나야 한다.

사진은 `public/images/` 아래에 두고 `/images/파일명.jpg` 로 참조한다. `public/`의
내용은 도메인 루트로 그대로 복사되므로 `/;/` 를 앞에 붙이지 않는다. `width`와
`height`를 적어 두면 사진이 늦게 도착해도 글이 밀리지 않는다. 사진은 본문 폭을
벗어나 단 전체를 쓴다 — 분위기가 아니라 근거로 걸리는 것이라 줄여 걸지 않는다.

### 판면 — 폭에 따라 다른 편집 문법

같은 조판을 접기만 하지 않는다. 폭에 따라 아예 다른 지면이 된다. 경계와 그 뜻은
`layout/viewport.ts`에 있고, CSS는 미디어 쿼리 조건에 사용자 지정 속성을 쓸 수
없어 각 파일이 숫자를 그대로 적는다(`grep 599px`, `grep 900px`).

| 판면      | 폭      | 성격                                           |
| --------- | ------- | ---------------------------------------------- |
| `compact` | ≤ 599px | 장면을 합치고 움직임의 폭을 낮춘다             |
| `snug`    | 600–899 | 여백 칼럼은 없지만 데스크톱의 구조는 남는다    |
| `wide`    | ≥ 900px | 넓은 판면 위에서 여백과 반응으로 의미를 만든다 |

**폭과 입력 방식은 다른 질문이다.** 폭은 «무엇을 어떤 순서로 놓을까»를 정하고
(`useViewport`), 입력 방식은 «같은 일을 무엇으로 시작하는가»를 정한다. 커서는
움직여서, 손가락은 찍어서 시작한다. 900px이 넘는 태블릿에도 커서는 없지만,
그것은 그곳에 반응이 없다는 뜻이 아니라 계기가 다르다는 뜻이다.

### 디자인 규칙 — 작은 판면

넓은 판면의 디자인을 좁은 화면에 욱여넣지 않는다. 좁은 화면에서 줄이는 것은
**장면의 수와 움직임의 폭**이다.

**«넓은 판면에서는 여백과 반응으로 의미를 만들고, 작은 판면에서는 같은 것을
더 적은 장면 안에서 더 얌전하게 한다.»**

산만함은 미니멀리즘이 부족해서 생기지 않는다. 넓은 지면에서 각자 자리를 갖던
미니멀한 장치들이 한 줄 안에 모이면서 각각 하나의 «요소»로 인식되기 때문이다.
그래서 모바일은 PC보다 못한 SEMICOLON이 아니라 **더 절제된** SEMICOLON이어야 한다.

절제와 삭제는 다르다. 이 구분을 놓쳐서 좁은 화면의 반응을 통째로 없앤 채
배포한 적이 있다. 장면을 합치는 것, 선을 걷어내는 것, 밀려나는 폭을 절반 아래로
낮추는 것은 절제다. 손가락으로 찍었을 때 아무 일도 일어나지 않게 만드는 것은
삭제이고, 그것은 얌전한 판면이 아니라 고장 난 판면이다. `npm run audit`이
세 판면 모두에서 이 선을 지킨다.

1. **한 화면에는 주인공이 하나뿐이다.**
   제목·메타데이터·이미지 조각·선·기호·움직이는 배경·화살표가 동시에 보이면
   안 된다. 목록의 한 행에 남는 것은 언제, 무엇, 사진 한 장뿐이다.

2. **선의 대부분을 지운다.**
   넓은 지면에서 선은 좌우를 나누는 구조였다. 한 줄뿐인 화면에서는 «여기 또
   구역이 있습니다»라는 표시가 되어 구획만 늘린다. 구획은 여백이 만든다.

3. **움직임의 폭은 줄이되 장치는 남긴다.**
   갈라지는 선, 밀려나는 색면, 지나가는 자리만 또렷해지는 이미지, 가로지르면
   뒤집히는 시안 — 넓은 화면에서 같은 거리로 밀리면 좁은 화면에서는 화면
   전체가 흔들리는 일이 된다. 그래서 폭을 낮춘다(`Field`의 `COMPACT_DAMPING`).
   없애지는 않는다. 커서에는 모양이라는 힌트가 있고 손가락에는 없으므로,
   지우는 대신 **시작점을 옮긴다** — 찍기 전의 밝기를 올려 무엇이 있는지 미리
   보이게 하고(`Materialize`, `Rift`), 반대쪽이 있다는 사실을 «01 / 02» 같은
   최소한의 표시로 알린다(`Faces`). 찍으면 커서와 같은 일이 일어난다.

4. **머리가 따라다니지 않는다.**
   화면 위에 늘 붙어 있는 막대는 그 자체로 «사이트»의 신호다. 문서의 맨 위에
   한 번 있고, 읽기 시작하면 지면만 남는다.

5. **장면을 합치되 문장은 덜어내지 않는다.**
   줄여야 하는 것은 장면의 수이지 읽을 것의 양이 아니다. 판면이 좁다는 것이
   글을 덜 받아도 된다는 뜻은 아니고, 모바일 우선 색인에서 여기서 뺀 문장은
   검색에서도 사라진다. `Session.compact`는 배치만 다르게 하는 자리다.

6. **스스로 시작하는 움직임은 기록당 두세 개까지.**
   사람이 시작하는 반응(찍고, 밀고, 다가가는 것)에는 수를 매기지 않는다. 세는
   것은 가만히 있어도 일어나는 쪽 — 스크롤을 따라 열리는 장면이다. 첫 기록에서
   크게 일어나는 것은 시안이 실물이 되는 장면과 마지막 기호, 둘뿐이다. 남은
   둘이 정말 사건으로 읽히려면 그 사이가 조용해야 한다.

7. **활자는 축소판이 아니다.**
   `clamp()`의 자동 축소는 기술적으로 옳지만 에디토리얼로는 축소판이다.
   좁은 판면에서는 단계 수를 줄이고 값을 고정한다. 다만 메타데이터를 12px
   아래로 내리지 않는다 — 화면이 좁다는 것이 글자를 못 읽어도 된다는 뜻은 아니다.

### SESSION의 부품

`components/session/`에는 기록이 쓰는 부품이 있다. 한 기록만을 위해 만든 것이
아니라 다음 기록도 쓸 수 있는 형태로 둔다.

| 부품                          | 하는 일                                                  |
| ----------------------------- | -------------------------------------------------------- |
| `Scene` · `Passage`           | 장면과 문단. 카드가 아니라 여백으로만 나뉜다             |
| `Opening`                     | 판면을 통째로 쓰는 기록의 머리. 표지가 먼저, 제목이 나중 |
| `Materialize`                 | 아직 물건이 아닌 이미지. 다가간 자리만 또렷해진다        |
| `Becoming`                    | 스크롤한 만큼 한 이미지가 다른 이미지가 된다             |
| `Faces`                       | 앞뒤 뒤집기. 보이는 버튼 없이, 진짜 버튼은 있다          |
| `Counter` · `Amount` · `Span` | 숫자 하나가 사건이 되는 자리                             |
| `Candidates` · `Quotes`       | 고르지 않은 것들과, 주고받은 말에서 남은 것              |
| `Quiet`                       | 이 구간을 읽는 동안 판면 뒤의 색을 뺀다                  |
| `Ending`                      | 기록의 마지막. 아래 획만 있던 기호가 세미콜론이 된다     |

움직임은 두 갈래로 나눠 쓴다. 스크롤을 따라 **연속으로** 변하는 것은 CSS의
스크롤 타임라인(`animation-timeline: view()`)이 맡고, 상태가 **딱 한 번** 바뀌는
것은 관찰자(`motion/useInView.ts`)가 맡는다. 둘을 섞지 않는다.

타임라인을 모르는 브라우저와 움직임을 줄이기로 한 사람에게는 전부 «끝난 상태»가
그냥 보인다. 겹쳐 바뀌던 두 장은 위아래로 놓이고, 뒤집던 것은 둘 다 펼쳐진다.
연출이 사라져도 읽을 수 있는 것이 하나도 줄지 않아야 한다.

### 디자인 규칙 — SEMICOLON

1. **«이것이 반드시 존재해야 하는가»를 먼저 묻는다.**
   미니멀리즘은 스타일이 아니라 의사결정 방식이다. 감성적인 사이트니까 필름 효과를,
   개발자 사이트니까 터미널을, 에디토리얼하니까 번호를 붙이는 식의 판단을 하지 않는다.
   그리고 미니멀리즘은 요소를 적게 쓰는 것이 아니라, 하나의 요소가 여러 역할을 하게
   만드는 것이다 — 이 공간에서 그 하나는 `;`다.

2. **`;`는 로고가 아니라 인터페이스다.**
   헤더에도, 히어로에도, 두 개념 사이의 이음매에도, 글이 끝나는 자리에도 나온다.
   다만 늘 같은 행동을 하지는 않는다. 히어로에서는 선을 벌려 두고, 이음매에서는
   스크롤을 따라 들어서고, 헤더에서는 페이지가 바뀔 때마다 다시 찍히고, 글 끝에서는
   문장이 여기서 잠시 멈춘다고 알린다. 기호 하나가 이 공간의 디자인 시스템 전체다.

3. **색은 장식이 아니라 재료다.**
   민트와 핑크는 글자에 얹지 않는다. 종이색 뒤에서 거의 인식되지 않을 정도로 존재하다가,
   사람이 움직이면 한 박자 늦게 밀려난다. 커서를 따라다니게 하지 않는 것이 핵심이다 —
   따라오면 마우스를 꾸미는 장식이 되고, 밀려나면 사람이 표면 아래를 지나간 흔적이 된다.
   색면의 경계가 눈에 보이면 그 순간 색면이 아니라 도형이므로, 반경을 크게 잡고
   두 색이 만나는 자리를 화면 밖으로 민다.

4. **움직임은 사람이 시작한다.**
   저절로 도는 애니메이션은 없다. 사용자가 움직이지 않으면 프레임 루프 자체가 멈춘다
   (`motion/useSettling.ts`). 다가가면 반응하고, 스크롤하면 흐르고, 터치하면 갈라지고,
   떠나면 다시 정지한다.

5. **인터랙션은 많아도 되지만 움직임의 양은 적어야 한다.**
   쓰는 것 — 색면 변형, blur, opacity, mask, 선의 확장, 점의 이동, `;`의 등장,
   미세한 scale. 쓰지 않는 것 — 날아오는 카드, 큰 패럴랙스, 3D 회전, bounce, 자동
   carousel, 뜻 없는 스크롤 애니메이션. 모든 움직임에는 이유가 있어야 한다.

6. **인터페이스는 이미지를 필요로 하지 않는다.**
   첫 화면이 미리 받아야 할 이미지가 없다. 사진은 실제 SESSION의 본문 안에서만 등장하고,
   그때는 생성 이미지가 아니라 실제 사진을 쓴다. 생성 이미지는 공유 카드 같은 보조
   자산까지만 맡는다.

7. **문장으로 설명할 수 있는 것은 형태와 동작으로 먼저 시도한다.**
   화면에 글자를 남기기 전에 «이것을 형태나 움직임으로 전달할 수 있는가»를 묻는다.
   가능하면 지운다. 화면에 남는 것은 대체로 콘텐츠 제목, 날짜, 장소, 본문,
   그리고 필요한 navigation label뿐이다. 브랜드 철학을 설명하는 카피는 두지 않는다.

8. **화면에서 뺀 문장은 지우지 않고 낭독에만 남긴다.**
   히어로의 «바쁜 삶 속의 세미콜론.»은 숨은 제목으로 남아 스크린리더와 검색에 그대로
   전해진다. 개념의 정의도 각 목록 페이지에 한 번씩 남는다 — 다만 선이 먼저 말하고
   문장은 그 아래에 물러나 앉는다. 상태를 밝혀야 하는 자리(빈 목록)는 숨기지 않는다.

9. **SESSION은 닫히고 THREAD는 흐른다.**
   이 차이를 문장이 아니라 규칙으로 적어 둔다. SESSION의 행은 `overflow: hidden`이라
   다가가면 색이 그 안으로 모이고 경계 밖으로 나가지 않는다. THREAD는 자르지 않아서
   색이 판면 밖으로 새어 나간다. 기호도 같다 — SESSION의 점은 벽에 부딪혀 멈추고,
   THREAD의 점들은 판을 넘어간다. 행의 규칙성(`Thread.form`)도 같은 대비를 따른다.

10. **모바일은 데스크톱의 축소판이 아니다.**
    손가락에는 hover가 없으므로 touch에 맞는 계기를 따로 준다. 찍으면 반응하고
    스스로 가라앉는다(`motion/useTouchReveal.ts`, Rift의 hold 타이머). 다만 첫 탭을
    가로채지 않는다 — 반응은 누르는 순간 일어나고 링크는 평소대로 열린다. 네이티브
    스크롤도 방해하지 않는다. 포인터·스크롤 리스너는 전부 passive이고, 만질 수 있는
    판은 `touch-action: pan-y`로 세로 스크롤을 그대로 넘긴다.

11. **글꼴은 두 벌뿐이고, 위아래가 아니라 나란히 놓는다.**
    Hahmlet이 제목·본문·큰 `;`를 맡고, IBM Plex Mono가 날짜·경로·메타데이터·메뉴를
    맡는다. 세리프는 명조이되 코딩 글꼴 쪽으로 기울어 있는 것을 골랐다 — 획 대비가
    낮고 종단이 평평해야 옆에 놓인 고정폭과 한 식구로 읽힌다. 나눔명조·고운바탕처럼
    붓의 흔적이 남은 명조는 옆의 고정폭과 서로 남남이 된다.
    둘을 같은 줄 위에 세우는 것이 핵심이다. 모노는 화면을 코드 에디터처럼 만들기
    위한 것이 아니라, 에디토리얼 지면 위에 만든 사람의 사고방식을 남기기 위한 것이다.

12. **고정폭의 자간은 라틴과 숫자에만 준다.**
    `2026-04-12`와 `/;/session`은 자간이 넉넉해야 읽히지만, 같은 자간을 한글에 주면
    낱글자가 흩어진다. 메타데이터라도 사람이 쓴 말(장소, 기간)이면 본문의 글자
    체계를 따르게 한다. 사진 설명도 같다 — 자리는 메타데이터지만 문장이다.

13. **판면의 경계는 그리지 않고 만든다.**
    화면 전체를 관통하는 고정 세로선과 전폭 박스선은 쓰지 않는다. 구획을 색면으로
    나누지도 않는다 — 색은 판면 전체에 깔린 재료여서, 상자를 칠하는 순간 두 개념의
    차이가 «어느 상자에 들어 있는가»가 되어 버린다. 큰 여백과 그 안에서 일어나는
    일이 구획을 만든다.

14. **날짜와 메타데이터는 본문 옆 여백 칼럼으로 내린다.**
    인쇄물의 방주(旁註)와 같은 자리다. 읽는 동안 눈은 본문 한 줄기만 따라가고,
    언제 어디였는지는 필요할 때만 곁눈으로 확인하게 된다.

15. **없는 정보는 지어내지 않는다.**
    `Meta`의 모든 항목은 선택이다. 채우려고 값을 지어내지 않고, 있는 정보라도
    그 콘텐츠를 이해하는 데 필요할 때만 화면에 올린다.

16. **`001` 같은 고정 자릿수 번호를 쓰지 않는다.**
    미래의 콘텐츠를 지금의 디자인 규격에 맞추지 않는다. 순서가 의미를 갖게 되는 날
    자연수로 붙이면 된다.

17. **필요해지기 전에 메뉴와 분류를 만들지 않는다.**
    `;` · SESSION · THREAD로 충분하다. ABOUT, ARCHIVE, 카테고리는 탐색이 실제로
    불편해졌을 때 만든다.

### 색과 대비

색면이 판면 뒤에 깔리므로 명암비는 «맨 종이 위»가 아니라 «색면이 가장 짙은 자리 위»에서
따진다. `--field-mint`를 짙게 만들면 `--color-text-muted`도 같이 봐야 한다.

| 잉크                     | 종이 위 | 색면 위 |
| ------------------------ | ------- | ------- |
| `--color-text`           | 18.1:1  | 16.6:1  |
| `--color-text-secondary` | 11.4:1  | 9.9:1   |
| `--color-text-muted`     | 6.85:1  | 6.5:1   |

| `;`  | SESSION과 THREAD 사이     | 스크롤을 따라 이음매에 들어선다. 끝났지만 끝나지 않았다   |
| `;`  | 헤더 · 파비콘             | 이 공간의 이름. 페이지가 바뀔 때마다 다시 찍힌다          |
| `;`  | 글 끝                     | 문장이 여기서 잠시 멈춘다                                 |
| 선   | 개념의 머리 · 목록의 경계 | 닫힌 선은 SESSION, 열린 선은 THREAD                       |
| `→`  | 목록의 행 · 절의 머리     | 이 줄이 다른 주소로 이어진다                              |
| `←`  | 되돌아가는 링크           | 온 길                                                     |

### 주소와 라우팅

`;`는 URL 경로에서 인코딩이 필요 없는 문자라 `/;`가 그대로 주소가 된다. 빌드는
`;/index.html`을 두 번째 엔트리로 잡아 `dist/;/index.html`을 만든다.

`/;/session/...` 같은 깊은 주소에는 대응하는 파일이 없어 GitHub Pages가 `404.html`을
돌려준다. 그 페이지가 원래 경로를 `?p=`에 실어 `/;/`로 넘기면 라우터가 주소창을
복원한 뒤 평소처럼 그 화면을 그린다. `?p=`를 달고 다시 404에 도착하면 더 보내지
않는다 — 무한 리다이렉트를 막는 장치다.

개발 서버에서는 `vite.config.ts`의 `semicolon-dev-fallback`이 `/;/...` 요청에 두 번째
문서를 제공한다. 브라우저 주소는 그대로 두므로 깊은 주소와 인코딩된 `/%3B/...` 경로를
배포 환경과 같은 라우터로 바로 검증할 수 있다.

## MAMABOY (`/mamaboy`)

키덜트·스킨케어·웰니스·안티에이징·longevity와 동시대 문화를 함께 다루는 큐레이션
매거진. 기사를 직접 쓰지 않고, 국내외 블로그·매거진·전문 사이트의 공개 피드에서
발견하고 골라 하나의 편집된 지면으로 낸다. 해외 콘텐츠는 한국어로 옮기되 원문으로
가는 길을 항상 남긴다.

**«나이는 먹는다. 늙는 방식은 고른다.»**

이름 자체가 이 공간의 구조다.

|      |           |                                                    |
| ---- | --------- | -------------------------------------------------- |
| MAMA | CARE      | 피부를 관리하고, 몸을 움직이고, 잘 자고, 오래 산다 |
| BOY  | CURIOSITY | 아직 굳어지지 않은 상태. 성별이 아니다             |

BOY는 성별이 아니라 «아직 굳어지지 않은 상태»를 가리킨다. 그래서 MEN / WOMEN /
FOR HIM / FOR HER 같은 라벨은 이 프로젝트에 존재하지 않고, 성별을 콘텐츠의 분류
기준으로 쓰지 않는다. 독자는 나이나 성별이 아니라 태도로 정의한다.

### 수집이 아니라 선별

핵심 기능은 RSS Aggregation이 아니다.

```
DISCOVER → FILTER → CURATE → TRANSLATE → PRESENT → SOURCE
```

들어온 것을 모두 게시하지 않는다. 모든 글은 두 질문 중 최소한 하나를 통과해야 한다.

- **CARE** — 이 콘텐츠가 자신을 더 오래 건강하게 유지하는 데 의미 있는 정보를 주는가
- **CURIOSITY** — 이 콘텐츠가 새로운 관심·놀이·문화·취향을 발견하게 하는가

둘 다 낮으면 제외한다. 판정은 `scripts/mamaboy/classify.mjs`의 규칙이 하고, 나중에
모델을 붙이더라도 이 규칙을 없애지 않는다 — 노출 여부를 모델 하나의 판단에 통째로
맡기지 않는다.

```
src/mamaboy/
  content/site.ts       이 공간의 모든 카피
  content/types.ts      Article · Category · Axis · ContentPolicy 타입
  content/seed.ts       예시 데이터 — 실제 RSS가 붙기 전까지 이 지면을 그린다
  content/feed.ts       지면이 읽는 유일한 입구
  content/generated/    파이프라인의 결과물 (Actions가 커밋한다)
  data/sources.json     RSS Source Registry
  services/             editorial(자동 편집) · search · present · time
  motion/               광택과 reduced motion
  styles/               tokens → (공용 reset) → global
  components/           컴포넌트 + 같은 이름의 CSS Module
  pages/                라우트별 화면
  router.tsx            경로 해석 · Link · 깊은 주소 복원
scripts/mamaboy/        fetch → normalize → classify → deduplicate → translate
```

### 콘텐츠 체계

1차 분류는 다섯 개다. 그 위에 두 개의 축이 있다.

| 축        | 카테고리          |
| --------- | ----------------- |
| CARE      | SKIN · BODY · AGE |
| CURIOSITY | PLAY · CULTURE    |

다만 홈에서 두 축을 물리적으로 양분하지 않는다. 이 매거진의 핵심은 둘의 공존이라
메인 피드에서는 의도적으로 섞는다 — 레티놀 다음에 캐릭터 완구, 그다음에 수면.
일반적인 웰니스 매거진에서 어색한 배열이 여기서는 정체성이다.

축은 화면을 나누는 데 쓰지 않는다. 쓰이는 곳은 지면을 섞을 때 한 군데뿐이다
(`services/editorial.ts`). 카테고리를 옮겼을 때 바뀌는 것은 색이 아니라 소재의
강도이고, 그것은 카테고리마다 따로 정해 둔다(아래 «소재와 깊이»).

### 지면을 짜는 방식

사람이 매일 레이아웃을 짤 수 없으므로 metadata가 편집 가중치를 정한다.

| 가중치   | 조판                                                     |
| -------- | -------------------------------------------------------- |
| FEATURE  | 제목과 이미지가 어긋나게 놓인다. 그날의 지면을 여는 자리 |
| STANDARD | 이미지가 위로 가거나(stacked) 옆으로 붙는다(side)        |
| BRIEF    | 이미지 없이 번호와 제목만 남는다                         |
| DROP     | MAMABOY의 기준에 맞지 않아 지면에 올리지 않는다          |

크기만 다른 같은 카드를 세 개 만드는 것이 아니라 **조판 자체를 다르게 짠다.**
크기만 다르면 그것은 결국 카드 목록이고, 지면의 리듬은 크기가 아니라 이 차이가
만든다. DROP이 있어야 이곳이 RSS Aggregator에서 벗어난다 — 무엇을 버렸는지가
무엇을 골랐는지를 만든다.

점수는 CARE/CURIOSITY 중 **높은 쪽**과 최신성, 콘텐츠의 성격에서 나온다. 두 축의
평균을 쓰지 않는 이유는 그렇게 하면 양쪽 모두 어중간한 글이 1등이 되기 때문이다.
한쪽으로 확실한 글이 이겨야 한다.

자리는 무작위가 아니다. STANDARD와 BRIEF가 각자 순환하는 표에서 열 시작점을
받아 오고, 그 시작점이 서로 달라서 한쪽이 왼쪽에서 시작하면 다른 쪽이 오른쪽
끝에 붙는다(`components/EditorialFeed.tsx`). 격자를 지키면서 격자로 보이지 않게
하는 장치다. 같은 데이터에서는 늘 같은 지면이 나온다.

### 구조는 즉시, 개성은 나중에

처음 온 사람에게 이 지면의 문제는 각 요소의 완성도가 아니라 **어디서 어디까지가
한 묶음인지 보이지 않는 것**이었다. 다섯 카테고리의 기사를 하나의 긴 흐름으로
섞고 있었기 때문이다.

기사를 하나씩 카드로 만들면 그 문제는 풀리지만 이곳의 비정형 조판이 함께 죽는다.
그래서 카드로 쪼개는 대신 **카테고리 전체를 종이 한 장으로 묶는다**
(`components/CategorySection.tsx`). 바깥은 즉시 이해되고, 안쪽은 그대로 자유롭다.

- 면은 판면의 좌우 여백을 그대로 두고 안쪽에만 자기 여백을 갖는다. 화면을 꽉
  채우면 «구역»이 아니라 «배경»이 되어 구분이 사라진다.
- 색은 카테고리마다 다르지만 «이 블럭은 파란색»이라고 느낄 정도가 아니다. 전부
  크림에서 출발해 아주 조금씩만 기운다. 강한 고유색을 주면 포털의 카테고리 UI가
  된다. 그림자도 카드처럼 떠 보이지 않는다 — 종이 위에 다른 질감의 종이가 한 장
  얹힌 정도다.
- 면의 제목은 카테고리 이름 하나뿐이다. 정의문을 두면 지면이 시작되기 전에 읽을
  것이 생기고, 그 순간 이 면은 «구역»이 아니라 «소개»가 된다. 면 안의 기사에는
  카테고리 태그를 붙이지 않는다 — 면이 이미 SKIN이라고 말하고 있다.
- 면마다 안쪽 리듬이 다르다(`pages/Home.tsx`의 RHYTHM). 면이 구분을 맡아 주므로
  안쪽까지 같은 모양일 이유가 없고, 다 같으면 다섯 번 반복되는 표가 된다.

CARE와 CURIOSITY를 위아래로 가르지 않는다는 원칙은 그대로다. 다만 기사 하나하나를
섞는 대신 **면의 순서로 섞는다** — SKIN · PLAY · BODY · CULTURE · AGE. 두 축이
교차하되 지금 보고 있는 것이 무엇인지는 분명하다.

브랜드 이름은 헤더에 한 번만 나온다. 홈 본문에 있던 제호와 «CARE + CURIOSITY»는
지웠다 — 같은 화면에서 이름을 두 번 세우면 그만큼 기사가 늦게 시작된다. 개념까지
버린 것은 아니다. 공유 카드와 소개 자리에는 그대로 남는다.

### 떠오르는 젤

젤은 기사들 사이의 격자 한 칸을 차지하고 있었다. 장식이 콘텐츠의 자리를 밀어내고
있었다는 뜻이다. 이제 격자 밖으로 나와 판면 뒤에 독립적으로 뜬다
(`components/FloatingGel.tsx`).

**저절로 도는 애니메이션은 두지 않는다.** 이 지면의 움직임은 언제나 사람이
만든다. 스크롤을 내리면 물속의 공기방울처럼 위로 오르고, 멈추면 함께 멈춘다.
크기가 다르면 오르는 속도도 다르고, 그 차이가 깊이를 만든다. 좌우로도 아주 조금
흔들리고 아주 조금 돈다 — 그것이 없으면 흔한 패럴랙스처럼 보인다.

**자리는 면과 면 사이다.** 미리 적어 두지 않고 그릴 때 잰다 — 면들 사이의 틈을
찾아 그 한가운데에 젤의 중심을 놓으면, 가운데 띠만 보이고 위아래는 면 뒤로
들어간다. 가리려고 애쓸 필요 없이 저절로 그렇게 된다. 틈의 위치는 그림이 도착하고
글꼴이 바뀔 때마다 달라지므로 `ResizeObserver`로 다시 잰다.

여기까지 오는 데 두 번 틀렸다. 처음에는 화면 높이(vh)로 자리를 잡았는데 네 개가
열여덟 화면짜리 페이지의 위 18% 안에 몰렸다. 그다음에는 «내려온 총 거리»에
비례해 올렸더니, 아래로 갈수록 젤이 제자리에서 수천 px 위로 날아가 면 뒤에 영영
숨었다 — 오르는 거리는 페이지가 아니라 **그 젤이 화면을 지나는 동안**에 매여 있어야
한다. 그래서 자바스크립트로 스크롤을 듣지 않고 저장소가 이미 쓰는 스크롤
타임라인(`.reveal`과 같은 장치)에 맡긴다.

세 폭(1440·768·390)에서 스크롤 구간의 25~32%에 젤이 드러나고, 한 화면에 동시에
보이는 것은 언제나 하나뿐이다.

색은 여러 개 쓰지 않는다. 같은 주황이 빛을 다르게 반사하는 것처럼 보이게 한다 —
원색을 나눠 주면 풍선이 되고, 소재를 나누면 젤이 된다.

좁은 화면에서도 띄운다. 한 번은 «자리가 없다»고 판단해 꺼 두었는데, 그것은 젤을
면 «위»에 두려 했기 때문이었다 — 좌우 여백이 20px뿐이니 당연히 드러날 곳이 없었다.
틈에 앉히고 나니 좁은 화면이 오히려 잘 보인다. 지우는 것이 아니라 자리를 옮기는
것이 답이었다.

### 이어서 읽을 것

기사 아래의 세 줄은 같은 카테고리의 최신순이 아니다. 세 가지를 함께 본다 —
낱말이 겹치는 정도, 어느 축에서 왔는지, 어느 출처에서 왔는지
(`services/related.ts`).

자리도 나눠 둔다. 첫 자리는 **가장 닮은 글**에게 주고, 나머지는 점수 순으로
채우되 출처는 서로 달라야 하고 적어도 하나는 **반대쪽 축**에서 와야 한다.
점수만으로 세 개를 자르면 축의 웃돈이 유사도를 눌러 «닮은 글»이 한 편도 못
들어온다 — 짧은 제목 두 개가 겹치는 정도는 대개 작기 때문이다. 닮은 것 하나와
뜻밖의 것 하나가 같이 있어야 이어 읽기가 성립한다.

임베딩은 쓰지 않는다. 정적 호스팅이고 계산이 브라우저에서 일어나므로 낱말이
겹치는 정도로 닮음을 근사한다. 한국어는 조사가 붙어 낱말이 그대로 일치하지
않으므로 두 글자 단위로 쪼개어 본다 — «레티놀을»과 «레티놀은»이 서로 남남이
되지 않게 하는 가장 싼 방법이다.

### 무엇을 버리는가

수집한 것을 전부 보여주는 것은 편집이 아니다. `dropReason`이 «아니오»라고
말할 수 있어야 이곳이 RSS Reader가 아니게 된다.

| 이유                    | 언제                                         |
| ----------------------- | -------------------------------------------- |
| 두 축 모두 낮음         | CARE·CURIOSITY 어느 쪽으로도 0.4에 못 미친다 |
| 건강 지면에 신뢰도 부족 | SKIN·BODY·AGE인데 소스 신뢰도가 2 미만이다   |
| 건강 지면의 제품 홍보   | 제품 소개인데 CARE 점수가 0.8에 못 미친다    |

떨어뜨린 이유는 건수와 함께 로그에 남는다. 통과 여부만 세면 필터가 지나치게
조이는지 느슨한지 알 수 없기 때문이다.

건강 정보에서는 «누가 말했는가»가 정보의 일부다. 그래서 소스마다 신뢰도
(`trustLevel` 1–5)를 두고, 낮은 소스의 제품 홍보성 글이 SKIN·BODY·AGE의 지면에
오르지 못하게 한다. 신뢰도는 순위를 뒤집는 데는 쓰지 않는다 — 점수에는 ±15%만
반영된다. 같은 이야기를 두 곳이 냈을 때 어느 쪽을 앞에 둘지 정도의 크기이고,
그보다 크게 쓰면 이 지면은 콘텐츠가 아니라 매체 목록이 된다.

소스마다 두 축에 기여하는 정도(`careWeight`, `curiosityWeight`)도 따로 둔다.
학술지가 낸 완구 기사와 완구 매체가 낸 노화 기사를 같은 무게로 다루지 않기
위해서다.

### 한 지면에 같은 것이 몰리지 않게

자동 편집은 점수만 보면 한쪽으로 쏠린다. 그래서 지면을 섞을 때 네 가지를 지킨다.

1. 바로 앞과 다른 축
2. 같은 카테고리가 세 번 연달아 오지 않는다
3. 바로 앞과 다른 출처
4. 첫 네 건에서는 한 출처가 두 번 나오지 않는다

네 가지를 모두 만족하는 후보가 없으면 하나씩 풀어 준다. 규칙 때문에 지면이
비는 것보다는 규칙이 한 번 어긋나는 편이 낫다 — 순서는 편집의 도구이지 지켜야
할 계율이 아니다.

### 중복

같은 연구를 여러 매체가 다룬다. 주소만 비교하면 걸러지지 않으므로 정규화한
주소, 매체 이름을 떼어 낸 제목, 제목 낱말의 겹침을 함께 본다. 많은 피드가 제목
끝에 «| 매체명»을 붙이는데, 그대로 두면 같은 보도끼리는 덜 닮아 보이고 같은
매체의 다른 기사끼리는 더 닮아 보인다.

겹침의 기준은 시간에 따라 움직인다. 여덟 시간 안쪽이면 0.62, 그 뒤로 사흘까지는
0.74다. 같은 연구가 하루 사이에 퍼질 때는 제목이 조금만 닮아도 같은 보도지만,
사흘 뒤의 비슷한 제목은 후속 보도나 다른 각도의 분석일 가능성이 크기 때문이다.
남길 하나는 «먼저 낸 쪽»이 아니라 성격이 더 분명한 쪽(RESEARCH > EXPERT > NEWS >
OPINION > PRODUCT)으로 고른다.

### 콘텐츠 추가 — 소스 등록

기사를 직접 쓰지 않으므로 이 공간에 콘텐츠를 더하는 일은 곧 소스를 더하는 일이다.
`src/mamaboy/data/sources.json`에 한 줄을 추가한다. UI 코드는 건드리지 않는다.

```json
{
  "id": "example",
  "name": "Example Journal",
  "feedUrl": "https://example.com/feed/",
  "homepage": "https://example.com/",
  "language": "en",
  "categories": ["skin"],
  "careWeight": 1.15,
  "curiosityWeight": 0.9,
  "trustType": "expert",
  "trustLevel": 4,
  "contentPolicy": "summary",
  "enabled": false,
  "note": "왜 켜져 있는지, 혹은 왜 꺼져 있는지"
}
```

`enabled`의 기본값은 `false`다. 피드가 살아 있는지, 그 매체가 어디까지 재사용을
허용하는지 사람이 한 번 확인한 뒤에 켠다. 확인되지 않은 소스를 켜 두면 이 지면은
남의 글을 무단으로 옮기는 곳이 된다.

`contentPolicy`가 이 지면에 실을 수 있는 범위를 정한다. 모르면 가장 좁은 쪽으로 둔다.

| 값        | 무엇까지 싣는가                                        |
| --------- | ------------------------------------------------------ |
| `full`    | 허용된 전문                                            |
| `summary` | 제목 + 요약 + 대표 이미지 + 원문 링크                  |
| `link`    | 제목과 최소한의 메타데이터, 그리고 원 사이트로 가는 길 |

RSS가 전문을 준다고 해서 전문 재게시를 기본값으로 삼지 않는다.

### 파이프라인

프론트엔드는 RSS에 직접 접근하지 않는다.

```
SCHEDULED FETCH → NORMALIZE → CLASSIFY → FILTER → DEDUPE → TRANSLATE → JSON → 지면
```

`npm run feed`가 이 전부를 돌리고 `src/mamaboy/content/generated/feed.json`을 쓴다.
GitHub Actions(`.github/workflows/mamaboy-feed.yml`)가 여섯 시간마다 같은 일을 하고,
결과가 바뀌었을 때만 커밋한다. 그 커밋이 배포 워크플로를 깨워 지면이 갱신된다.

**쓰기 전에 한 번 막는다.** 수집이 «성공»했다는 것과 그 결과가 쓸 만하다는 것은
다르다. 소스 절반이 죽은 날, 파서가 빈 문자열을 채운 날, 날짜가 1970년으로 찍힌
날에도 스크립트 자체는 오류 없이 끝난다. 그래서 기록 직전에 검증한다
(`scripts/mamaboy/validate.mjs`) — 최소 건수, 필수 필드, 주소와 날짜의 형식,
id·slug 중복, 0..1을 벗어난 점수, 알 수 없는 분류값.

통과하지 못하면 **아무것도 덮어쓰지 않는다.** 지면은 마지막 정상 feed로 계속 서
있고 워크플로만 실패로 끝난다. 새 데이터가 없는 것보다 깨진 데이터가 배포되는 쪽이
훨씬 나쁘기 때문이다.

로그에는 무엇이 몇 건 들어와 몇 건이 떨어졌는지가 남는다 — 소스 응답 수, 수집,
편집 필터에서 제외, 기간·중복에서 제외, 번역 완료/실패/대기, 최종 건수. 문제가
생겼을 때 화면을 보고 역추적하는 구조를 피하기 위해서다. 소스별 성공·실패와 마지막
성공 시각은 `generated/sources-health.json`에 쌓여, 계속 실패하는 피드가 숫자로
드러난다.

### 소스를 켜기 전에

`npm run feed:probe`가 등록된 소스를 하나씩 두드려 응답·리다이렉트·형식(RSS/Atom)과
첫 항목의 제목·요약·author·이미지·날짜가 실제로 파싱되는지 보여준다. 이 저장소의
개발 환경은 바깥으로 나가는 요청이 막혀 있으므로, 확인은 Actions에서 한다
(`.github/workflows/mamaboy-probe.yml`, workflow_dispatch). 아무것도 커밋하지 않는다.

응답한다는 것과 재사용이 허용된다는 것은 다른 문제다. `enabled`를 켜는 결정은
사람이 하고, 그때 `contentPolicy`도 함께 정한다.

### 예시 데이터에서 벗어나는 순간

소스가 하나도 켜져 있지 않으면 파이프라인은 아무것도 쓰지 않고, 지면은 예시
데이터(`content/seed.ts`)로 그려지며 화면에 PROTOTYPE 표시가 붙는다.

소스를 **하나라도 켠 뒤에** 생성물이 없다면 그것은 파이프라인이 실패했다는 뜻이다.
그때는 예시 데이터로 대신 채우지 않고 비어 있다고 말한다 — 그 자리에 지어낸 기사를
세우면 사고를 감추는 것이 된다. 이 전환에 사람이 눌러야 하는 스위치는 없다.
`enabled`가 하나라도 true가 되는 순간 저절로 그렇게 된다(`content/feed.ts`).
개발 서버에서는 언제나 예시 데이터를 쓴다 — 화면을 고치는 사람이 매번 수집기를
돌려야 한다면 그것대로 잘못된 구조다.

### 번역

한국어가 아닌 글은 수집한 그 순간 한 번 번역하고 결과를 캐시에 남긴다. 페이지를 열
때마다 번역하는 구조는 비용과 응답 시간 양쪽에서 감당이 되지 않는다.

옮기는 일은 **Azure Translator**가 한다. 무료 티어(F0)가 달마다 200만 자를 주고
이 지면이 쓰는 양은 그 절반이 안 된다. 한도를 넘으면 자동으로 과금되는 것이 아니라
403이 오고 다음 달에 리셋된다 — 모르는 사이에 청구서가 생기지 않는다.

다만 200만 자를 «한꺼번에» 주지는 않는다. 분당 한도가 따로 있어서, 요청 사이만
띄우고 양을 보지 않으면 20초에 5만 자를 밀어 넣고 429를 맞는다. 그래서 요청 수가
아니라 **글자 수로 속도를 잰다**(분당 30,000자). 첫 실행은 33만 자라 11분쯤 걸리고,
그 뒤로는 캐시가 받아 주므로 새 글 몇 건씩 1~2분이면 끝난다. 429는 «너무 빠르다»와
«다 썼다» 두 가지에 다 쓰이므로 물러섰다 다섯 번까지 다시 해 보고, 403만 처음부터
한도로 본다.

한도를 넘긴 글은 **원문 그대로 걸리고 `ORIGINAL` 배지가 붙는다.** 번역이 없다고
해서 지면에서 사라지지 않는다. 다음 달에 저절로 풀린다.

`MAMABOY_TRANSLATOR=claude`로 두면 LLM으로 옮긴다. 제목을 «번역»이 아니라 «다시
쓰는» 일은 그쪽이 낫지만 돈이 든다. 어느 엔진으로 옮겼는지가 캐시 키에 들어가므로
엔진을 바꾸면 지난 결과를 재사용하지 않는다 — 그러지 않으면 한 지면에 두 종류의
번역이 섞인다.

| 환경 변수                 | 쓰임                                                    |
| ------------------------- | ------------------------------------------------------- |
| `AZURE_TRANSLATOR_KEY`    | Azure Translator 리소스의 키. 이것만 있으면 번역이 돈다 |
| `AZURE_TRANSLATOR_REGION` | 전역 리소스가 아니면 필요하다 (예: `koreacentral`)      |
| `ANTHROPIC_API_KEY`       | `MAMABOY_TRANSLATOR=claude`일 때만                      |

아무 키도 없으면 번역하지 않고 `pending`으로 둔다.

번역의 원칙은 세 가지다.

1. 직역보다 자연스러운 한국어. 다만 원문에 없는 의미를 만들지 않는다.
2. 성분명·연구기관·제품명·고유명사는 원문 표기를 보존한다.
3. 원문 데이터를 결과로 덮어쓰지 않는다. 번역은 새 필드로만 들어간다.

번역된 글에는 `AI TRANSLATED` 배지가 붙고, 원문 제목이 번역 제목 아래 그대로 남는다.

**용어는 부탁하고 끝내지 않는다.** 레티노이드를 «비타민A 유도체»로 풀어 쓰면 문장은
부드러워지지만 그 글이 어떤 성분에 대한 것인지 검색으로 찾을 수 없게 된다. 그래서
성분·의학·노화 연구 용어와 연구기관 이름을 목록으로 두고(`scripts/mamaboy/glossary.mjs`),
**옮기기 전에 문장 안에 지정해 넣는다.** Azure의 dynamic dictionary가 그 장치다 —
`<mstrans:dictionary translation="레티놀">retinol</mstrans:dictionary>`처럼 원문에
직접 박아 두면 그 낱말은 지정한 대로 나온다. 부탁이 아니라 지정이다.

그러고도 **돌아온 결과에서 그 용어가 실제로 남아 있는지 다시 확인한다.** 사라졌으면
번역을 쓰지 않는다 — 성분 이름이 빠진 문장을 «번역»이라고 부르며 올리는 것보다
원문을 그대로 보여주는 편이 정직하다.

낱말 경계에서만 지정한다. `collagen`을 찾는다고 `procollagenase` 안쪽을 건드리면
원문에 없던 말을 만들게 된다.

목록의 `ko`에는 «이렇게 옮겨도 된다»고 인정하는 표기를 적는다. 레티놀처럼 한국어
표기가 이미 굳은 말까지 원어를 강요하면 번역이 읽히지 않는다.

**캐시 키는 네 가지로 만든다** — 규칙의 판(`TRANSLATION_VERSION`), 쓴 엔진, 주소,
내용의 해시. 프롬프트나 용어집을 고치면 판을 올리고, 그 순간 예전
규칙으로 옮겨 둔 문장이 전부 다시 번역된다. 규칙을 바꿔 놓고 옛 결과를 그대로 쓰면
지면에 두 세대의 번역이 섞인다. 90일 넘게 쓰이지 않은 항목은 정리한다.

실패는 종류를 나눠 다룬다. 일시적인 오류는 한 번 더 시도하고, 용어가 사라졌거나
옮긴 문단 수가 맞지 않으면 그 글의 번역을 쓰지 않는다. **한도를 넘긴 것은 거기서
멈춘다** — 남은 글까지 하나씩 다시 물어봐야 같은 답이 오므로, 한 번 429를 받으면
그 실행의 나머지는 부르지 않고 전부 원문으로 남긴다. 어느 쪽이든 상태가 `failed`가
되고 화면에는 원문이 그대로 걸린다.

### 시각 언어

두 문장이 이 브랜드의 시각적 결정을 전부 지배한다.

**SOFT BODY, HARD LIGHT** · **Clean Editorial × Stupid Objects**

지면은 진지하고, 오브젝트만 미친다. 레이아웃과 활자는 정교하게 유지하고, 말랑하고
철없는 것은 만질 수 있는 물체에만 허락한다. 모든 것을 장난스럽게 만들면 그때부터는
매거진이 아니라 장난감 사이트가 된다.

### 색

| 토큰              | 값                     | 몫   | 자리               |
| ----------------- | ---------------------- | ---- | ------------------ |
| `--cream`         | `#f5efe4`              | 65%  | 지면               |
| `--ink`           | `#171513`              | 23%  | 글자와 선          |
| `--surface-clean` | `#fffdf9`              | 6%   | 맑아지는 표면      |
| `--orange`        | `#ff7417`              | 4%   | 젤·오브젝트·포인트 |
| `--yellow`        | `#ffc83d`              | 1.5% | 아주 가끔의 강조   |
| `--glass-white`   | `rgb(255 255 255/.42)` | 0.5% | 유리               |

사이트 전체가 주황으로 보이면 실패다. 첫인상은 Cream + Ink의 매거진이어야 한다.

명암비는 `--color-bg`(크림) 기준이다.

| 잉크                     | 명암비 |
| ------------------------ | ------ |
| `--color-text`           | 15.8:1 |
| `--color-text-secondary` | 8.7:1  |
| `--color-text-muted`     | 6.3:1  |
| `--accent-ink`           | 6.9:1  |

`--orange`는 크림 위에서 2.4:1이라 **글자로 쓸 수 없다.** 면과 오브젝트에만 쓴다.
본문 크기의 글자가 주황이어야 하는 자리에는 탄 주황(`--accent-ink`)을 따로 두고,
반대로 주황 «면» 위의 잉크는 6.7:1이라 그대로 읽힌다 — 버튼은 그쪽으로 만든다.

### 소재와 깊이

소재를 무작위로 섞지 않는다. 계층은 넷뿐이고 순서가 정해져 있다.

```
CREAM PAPER → ORANGE GEL → LIQUID GLASS → CHROME LIGHT
```

Chrome은 독립된 소재가 아니다. 젤과 유리의 가장자리와 반사에만 붙는 빛이다.

깊이도 세 단계뿐이고 늘리지 않는다.

| 깊이 | 무엇이 있나                     | 그림자                 |
| ---- | ------------------------------- | ---------------------- |
| 0    | 배경 · 본문 · 기본 타이포그래피 | 없음                   |
| 1    | 기사 이미지 · 콘텐츠 영역       | `--shadow-content`     |
| 2    | 젤 · 유리 · floating navigation | `--shadow-float/press` |

그림자는 장식이 아니라 상태다. 떠 있으면 넓고 흐리게(`float`), 눌리면 짧고
짙게(`press`) 바뀐다. 젤의 그림자에는 따뜻한 색을 섞는다 — 젤은 회색 그림자를
만들지 않는다.

카테고리마다 다른 소재를 주지 않는다. 팔레트와 물성은 하나이고 강도만 다르다 —
SKIN·BODY는 종이가 맑아지고(`clean`), AGE는 차가운 빛이 스치고(`chrome`),
PLAY·CULTURE는 젤이 번진다(`gel`). 사용자가 «색이 바뀌었다»고 알아차릴 정도로
벌리지 않는다(`components/Ambient`).

### 디자인 규칙 — MAMABOY

1. **내용은 진지하고, 생김새에는 장난기가 있다.**
   노화 연구를 소개하는 화면을 의료기관처럼 만들지 않고, 캐릭터 완구 기사를 어린이
   쇼핑몰처럼 만들지 않는다. 두 콘텐츠가 같은 시각 언어 안에 있어야 이 매거진이
   «스킨케어 + 키덜트 사이트»가 아니라 하나의 태도로 읽힌다. 판단 기준은 세 개의
   모순이다 — 깊지만 철없다 · 진지하지만 근엄하지 않다 · 고급스럽지만 점잖은 척하지
   않는다.

2. **로고는 서체가 아니라 그려 둔 레터링이다.**
   소문자, 두꺼운 단선, 둥근 종단. 그리고 boy에서 리듬을 한 번 깬다 — o의 자리에
   속을 반짝임으로 도려낸 원반이 들어가고 그 위로 작은 빛 하나가 떠 있다. 여섯
   글자가 같은 박자로 이어지다 일곱 번째에서 어긋나는 것이 이 레터링의 전부다.
   화면용은 `components/Wordmark.tsx`, 파비콘·공유 카드용은 `scripts/build-assets.mjs`가
   같은 좌표계를 쓴다 — 기준선 150 · x-높이 바깥 50 · 어센더 18 · 디센더 196 · 획 32.
   기본형은 Flat Ink다. 3D·젤·광택은 화면 안에서의 확장이지 로고 자체가 아니다.

3. **글꼴은 두 벌이고 역할이 다르다.**
   Plus Jakarta Sans가 제목과 라벨(EDITORIAL), Pretendard가 본문(READING)을 맡는다.
   로고의 장난기를 제목과 본문까지 반복하지 않는다. 그리고 UI식 중간 크기를 반복하지
   않는다 — 메타데이터는 12px, FEATURE 제목은 72px까지 간다. 그 낙차가 이 지면의
   인상을 만든다.

4. **Rounded ≠ Card UI.**
   곡선은 허용하지만 모든 요소를 둥근 카드로 만들지 않는다. 전역 카드 반경 같은 것을
   두지 않고, 곡률은 세 자리에만 쓴다 — 이미지 마스크, 젤·유리 오브젝트, 알약. 기사
   카드에는 배경도 테두리도 없다. 카드가 보이는 대신 기사가 보여야 한다.

5. **유리는 만질 수 있는 것에만 붙는다.**
   검색 필드, 언어 전환처럼 실제로 만지는 것만 Liquid Glass다. 헤더처럼 늘 떠 있는
   판까지 유리로 만들면 «어디를 만질 수 있는가»라는 신호가 사라진다. 그리고 유리는
   얇은 반투명 카드가 아니라 조금 두꺼운 젤리여야 한다 — 위 가장자리의 흰 선과 아래의
   그림자가 그 두께를 만든다.

6. **빛은 도형이 아니다.**
   표면 위를 지나가는 반사광의 위치는 포인터가 정한다(`motion/useGloss.ts`).
   가장자리에서 완전히 투명해지지 않으면 광택이 아니라 무늬가 된다.

7. **«Interaction as Touch».**
   SEMICOLON의 인터랙션은 의미를 옮기지만, 여기서는 물체를 만지는 감각을 준다.
   반응은 세 가지로 제한한다.

   | 반응   | 무엇이                              | 어디에                 |
   | ------ | ----------------------------------- | ---------------------- |
   | TOUCH  | 누르면 1~2% 눌린다                  | 전역 `.pressable`      |
   | LIGHT  | 포인터를 따라 표면의 빛이 옮겨 간다 | `motion/useGloss.ts`   |
   | REVEAL | 스크롤이 닿으면 짧게 올라온다       | 전역 `.reveal` (CSS만) |

   시간은 두 단계다. 손끝에서 끝나는 것은 120–280ms, 물체가 움직이는 것은
   400–900ms. 저절로 반복되는 애니메이션은 두지 않는다.

8. **첫 화면은 브랜드가 아니라 오늘의 편집판이다.**
   매일 같은 Hero를 보여주는 구조는 RSS 매거진과 맞지 않는다. 제호는 신문 1면의
   이름표만큼만 두고, 그 아래에서 곧바로 그날의 FEATURE가 시작된다. 3D와 유리를 첫
   화면에 전부 꺼내 놓지 않는다 — 스크롤하고 만질수록 발견되게 한다.

9. **카테고리는 알약 다섯 개가 아니라 목차다.**
   번호를 붙이고(01–05) 지금 보고 있는 장에 주황 젤 표식이 붙는다. 다른 장으로
   옮기면 그 표식이 사라졌다 나타나는 것이 아니라 새 자리로 미끄러져 간다 —
   «지금 여기»가 이동한 것으로 읽히려면 표식도 물체여야 한다. 항목마다 글자
   폭이 다르므로 자리는 CSS가 아니라 실제로 그려진 위치를 재서 넘긴다
   (`components/CategoryIndex.tsx`). 좁은 화면에서는 가로로 넘기고, 스크롤은
   브라우저의 것을 그대로 쓴다.

10. **모든 카드에 요약을 붙이지 않는다.**
    기본 카드에 있는 것은 CATEGORY · TITLE · SOURCE · TIME뿐이다. 요약이 붙는 것은
    FEATURE 하나다. 모든 카드가 설명을 달면 사용자는 지면의 구조를 읽지 못한다.

11. **출처 표기는 디자인 요소가 아니라 시스템 요구사항이다.**
    MAMABOY는 이 글을 쓰지 않았다. 카드에서 가장 먼저 지워지는 요소(이미지·요약)가
    있어도 출처 줄은 남고, 기사 화면에는 출처 블록과 원문으로 가는 버튼이 반드시
    있다. MAMABOY의 이름을 출처처럼 표시하지 않는다.

12. **이미지가 없어도 완성된 지면이어야 한다.**
    RSS의 대표 이미지는 언제든 깨진다. 실패하면 placeholder를 넣는 대신 이미지를
    통째로 없애고, 그 기사는 타이포그래피 조판으로 바뀐다. 잡지의 리듬은 오히려
    그렇게 만들어진다(실제로 모든 이미지를 끊어 놓고 지면이 성립하는지 확인한다).
    FEATURE 하나를 뺀 모든 이미지는 지연 로드하고, width/height를 미리 적어 지면이
    밀리지 않게 한다. 기다리는 자리에는 회색 skeleton을 깔지 않는다 — 크림보다 반 톤
    밝은 면으로 두고 도착하면 이미지가 그 위로 스며든다. «오는 중»이라는 상태도
    움직임이 아니라 밝기로 말한다.

13. **읽는 화면은 지면보다 훨씬 조용하다.**
    Home은 개성을 보여주는 곳이고 Reader는 읽는 곳이다. 기사 화면에서는 젤·유리·주황의
    양을 줄이고 Cream + Ink의 비중을 올린다. 표지 이미지가 제목보다 커지는 순간 이
    페이지는 읽는 자리가 아니라 보는 자리가 되므로, 표지도 판면 전체를 가져가지 않는다.

14. **버튼의 동작은 콘텐츠 권한이 정한다.**
    번역이 있는 글에는 KR / ORIGINAL이 나온다. 원문 전문을 실을 수 있는 글이면
    ORIGINAL은 같은 화면에서 원문으로 바꾸고, 그렇지 않으면 원 사이트로 나가는 링크가
    된다. 생김새가 아니라 동작이 자동으로 결정된다.

15. **건강 정보와 개인의 경험담을 같은 무게로 보여주지 않는다.**
    RESEARCH · EXPERT · NEWS · OPINION · PRODUCT 중 판단의 근거가 되는 성격에는
    라벨을 붙이고, SKIN·BODY·AGE의 기사에는 의학적 조언이 아니라는 한 줄을 남긴다.

16. **모바일은 hover를 지우는 것이 아니라 계기를 바꾼다.**
    편집의 무질서를 그대로 옮기지 않는다. 배치는 한 단으로 단순해지지만 기사 크기의
    차이는 그대로 유지한다. 카테고리는 헤더에 고정 노출하지 않고 눌렀을 때 펼친다 —
    12px 라벨 다섯 개는 320px 화면의 가로 폭을 넘긴다.
    반응도 지우지 않는다. 커서가 있는 곳에서는 지나가는 자리가, 손가락에는 «누른
    자리»가 빛의 위치가 된다. 손가락은 화면에 머물지 않으므로 떼면 빛도 스스로
    가라앉는다 — 다만 브라우저는 손가락을 뗄 때 pointerleave까지 함께 보내므로,
    그것을 그대로 받으면 여운이 즉시 지워져 «반응하지 않는 화면»이 된다. 떠나는
    것은 커서에게만 있는 일로 다룬다. native scroll은 어느 경우에도 방해하지 않는다.

### 찾기

검색은 화면 위에서 열리고 닫으면 보던 자리로 돌아온다. 별도의 검색 페이지를 두지
않는다. 헤더의 SEARCH로 열리고, 글을 쓰고 있는 칸 밖에서라면 `/` 로도 열린다.

**대상** 번역 제목 · 원문 제목 · 요약 · 카테고리 · 출처 · 키워드. 공백으로 끊은
모든 낱말이 들어 있어야 걸린다.

**순위** 걸린 순서대로 늘어놓지 않는다. 어디에서 걸렸는지에 무게를 준다 —
제목 5, 키워드 3, 출처와 카테고리 2.5, 요약 1.5. 낱말의 첫머리에서 걸리면 1.6배다
(«케어»는 «스킨케어»보다 «케어 루틴»에 가깝다). 낱말마다 가장 무거운 자리 하나만
세고 합을 내지 않는다 — 합을 내면 요약이 긴 글이 제목이 정확한 글을 이긴다.
최근 글에는 최대 12%까지 얹지만, 그것으로 관련도를 뒤집지는 못한다.

**좁히기** 걸린 것에서 카테고리와 출처를 뽑아 칩으로 보여준다. 숫자는 «지금 걸린 것
전부»를 기준으로 세므로 누를 때마다 흔들리지 않는다. 고를 것이 하나뿐이면 그 줄은
그리지 않는다 — 눌러도 아무것도 바뀌지 않는 버튼은 없는 편이 낫다. 질의가 바뀌면
좁혀 둔 조건은 풀린다.

**치기 전** 빈 상자로 열지 않는다. 방금 걸린 다섯 건을 먼저 보여준다. 검색은 찾는
기능이기도 하고 둘러보는 입구이기도 하다.

출처 목록(`/mamaboy/sources`)에는 매체마다 지금 몇 건이 걸려 있는지를 함께 적는다.
이름만 늘어놓으면 명단이지만 건수가 붙으면 현황이 된다 — 켜 두고도 한 건도 들어오지
않는 소스가 있다는 사실이 그 목록에서 바로 보여야 한다.

### 무게

측정은 `dist`를 preview로 띄우고 실제 브라우저에서 잰 값이다.

| 폭                   | FCP    | LCP    | CLS    | 스크롤 프레임 간격 |
| -------------------- | ------ | ------ | ------ | ------------------ |
| 1440 (CPU 그대로)    | 540ms  | 540ms  | 0.0001 | p50 16.7ms         |
| 390 (CPU 4배 느리게) | 1312ms | 1528ms | 0      | p50 16.7ms         |

전송량은 JS 240KB · CSS 86KB · 폰트 416KB다. 가장 큰 것은 폰트이고, 그중
대부분은 Pretendard의 한글 조각 열다섯 개다. 한글 지면에서 줄일 수 없는 몫이라
줄이지 않는다 — 대신 두 글꼴 모두 `font-display: swap`이라 글자는 조각이 도착하기
전에 이미 읽힌다. LCP 요소는 이미지가 아니라 FEATURE 기사의 제목이다.

넘치는 것을 막는 장치는 `#root`의 `overflow-x: clip` 하나다. 배경 겹처럼 일부러
판면보다 크게 잡은 것은 자기 자신을 자른다 — `clip`을 지원하지 않는 브라우저에서
그것이 가로 스크롤이 되기 때문이다.

### 주소와 라우팅

```
/mamaboy/                    오늘의 지면
/mamaboy/{category}          skin · body · age · play · culture
/mamaboy/article/{slug}      기사
/mamaboy/sources             콘텐츠가 어디서 오는가
```

`slug`는 원문 제목의 라틴 부분과 주소 해시로 만든다. 라틴 글자가 없는 제목에서는
해시만 남는다 — 한글을 그대로 주소에 넣으면 공유할 때마다 퍼센트 인코딩된 긴
문자열이 되기 때문이다.

깊은 주소의 복원은 SEMICOLON과 같은 장치를 쓴다. GitHub Pages에는
`/mamaboy/article/...`에 해당하는 파일이 없어 `404.html`이 뜨고, 그 페이지가 원래
경로를 `?p=`에 실어 `/mamaboy/`로 넘기면 라우터가 주소창을 복원한 뒤 평소처럼 그
화면을 그린다. 개발 서버에서는 `vite.config.ts`의 `project-dev-fallback`이 같은
주소에 마마보이 문서를 준다.

## 접근성 기준

- 본문 색 대비는 배경 기준 최소 6:1 (WCAG AA 4.5:1 상회) — 세 공간 모두.
  SEMICOLON은 색면이 가장 짙은 자리 위에서 잰다(위의 «색과 대비» 표)
- 최소 글자 크기 12px, 인터랙티브 요소 최소 높이 44px
- 헤드라인 글자 분할 애니메이션은 스크린리더에 원문을 한 번만 노출
- 키보드 포커스에도 호버와 동일한 상태를 표시하고, 손가락에는 touch로 같은 상태를 준다
- 제목이 없는 Thread도 문서 위계를 잃지 않도록 날짜를 숨은 제목으로 쓴다
- 빈 목록 상태는 시각적으로도 표시하고, 생성 이미지는 장식이므로 빈 `alt`로 둔다
- 화면에서 뺀 문장은 삭제하지 않고 숨은 제목으로 남긴다 — 히어로에는 보이는 글자가
  거의 없지만 문서에는 `h1`이 있다
- MAMABOY의 검색은 브라우저의 `<dialog>`를 쓴다. 초점 가두기·Escape·뒤쪽 비활성화를
  직접 구현하지 않는다 — 직접 만들면 거의 항상 어딘가 샌다
- 화면에서 라틴 라벨을 쓰는 버튼(MENU, CLOSE)에도 한국어 `aria-label`을 준다
- `prefers-reduced-motion: reduce`에서는 프레임 루프와 이벤트 리스너를 아예 붙이지
  않는다. 다가가야만 보이던 `;`는 처음부터 온전한 잉크로 서 있는다 — 움직임을 줄인
  사람이 정보를 덜 받게 되면 안 된다. 스크롤을 따라 열리는 글은 반드시 열린 상태를
  따로 적어 둔다. 안 적으면 그 사람에게는 투명한 채로 남는다(`npm run audit`이 본다)

## 화면 검사 (`npm run audit`)

`npm run check`는 코드가 말이 되는지만 본다. 타입이 맞고 린트를 통과해도 화면에서
글자가 잘리거나, 손가락으로 찍었을 때 아무 일도 안 일어나거나, 문장 하나가 조용히
빠질 수 있다. `scripts/audit.mjs`는 세 판면(390 · 768 · 1440)에서 실제 브라우저를
열어 그것을 본다. 개발 서버가 없으면 알아서 띄운다.

여기 있는 항목은 **전부 한 번씩 실제로 배포까지 나갔던 잘못**이고, 새 항목은
그렇게 해서만 추가한다. 공통점이 하나 있다 — 전부 «없어진 것»인데, 그때 확인하던
틀 안에서는 없어진 것이 보이지 않았다.

| 검사           | 무엇을 보는가                                               | 왜 놓쳤었나                                     |
| -------------- | ----------------------------------------------------------- | ----------------------------------------------- |
| 잘린 잉크      | 잘라내기·마스크가 글자의 획을 먹고 있지 않은지              | 요소 크기에 맞춰 찍으면 잘린 잉크는 프레임 밖   |
| 죽은 장치      | 마우스와 손가락 **양쪽**에 반응하는지, 그래서 눈에 보이는지 | 상태 속성만 보고 화면을 안 봤다                 |
| 사라진 문장    | 좁은 판면이 넓은 판면의 문장·이미지를 그대로 갖는지         | 손으로 세어 확인했다                            |
| 안 열린 글     | 움직임을 끈 사람에게 모든 문장이 실제로 보이는지            | 끝 상태를 안 적어 둔 곳은 코드만 봐선 안 보인다 |
| 한 번뿐인 장면 | 사건으로 만든 장면을 지나갔다 돌아오면 다시 볼 수 있는지    | 내려가면서 한 번만 보고 올라와 보지 않았다      |
| 화면에 닿은 글 | 판면의 여백이 실제로 있는지                                 | 넘치지 않으면 통과시켰다                        |
| 가려진 링크    | 보이는 링크를 실제로 누를 수 있는지                         | 투명한 층이 덮으면 화면은 멀쩡해 보인다         |
| 가로 넘침      | 어느 폭에서도 가로로 밀리지 않는지                          | —                                               |
| 기울어진 목록  | 그리지도 않는 기호의 자리를 비워 둔 목록이 없는지           | 20px은 «틀렸다»가 아니라 «어색하다»로만 보인다  |

두 가지가 이 검사의 요령이다. 첫째, **없어졌을 자리까지 넓게 본다** — 요소 둘레를
넉넉히 두고 찍어야 상자 밖으로 나간 잉크가 프레임에 들어온다. 둘째, **대신 볼 수
있는 것 말고 실제로 보이는 것을 본다** — 장치가 살아 있는지는 `data-` 속성이
바뀌었는가와 화면의 픽셀이 실제로 달라졌는가를 **둘 다** 확인한다. 속성만 보면
«바뀌었는데 화면은 그대로»인 상태를 통과시킨다.

검사 항목을 새로 넣거나 고칠 때는 **먼저 그 잘못을 일부러 되살려 놓고 검사가
실패하는지 확인한다.** 실패시킬 수 없는 검사는 통과해도 아무것도 보증하지 않는다.

### MAMABOY (`npm run audit:mamaboy`)

마마보이는 판면의 성격이 달라서 검사도 따로 둔다(`scripts/audit-mamaboy.mjs`).
네 폭(320 · 390 · 768 · 1440)에서 홈 · 카테고리 · 기사 · 출처 · 없는 주소를 열고
아래를 본다. `AUDIT_SCREENS=tiny,wide`로 폭을 골라 볼 수 있다.

| 검사                | 무엇을 보는가                                                            |
| ------------------- | ------------------------------------------------------------------------ |
| 잘려 나가는 내용    | 글자·그림·누를 것이 화면 밖으로 나가지 않는지                            |
| 작은 글자           | 12px 아래로 내려간 글자가 없는지                                         |
| 작은 타깃           | 누를 것이 44px 아래로 작아지지 않았는지                                  |
| 겹친 타깃           | 누를 것들의 히트 영역이 서로 겹쳐 옆의 것이 눌리지 않는지                |
| 안 열린 글          | 움직임을 끈 사람에게 모든 기사가 보이는지                                |
| 흐린 채 남음        | 스크롤을 내려도 화면 한가운데의 기사가 흐린 채 남지 않는지               |
| 죽은 검색           | `/`로 열리고, 걸리고, 칩으로 좁혀지고, Escape로 닫히는지                 |
| 그림이 다 죽었을 때 | 이미지를 전부 막아도 기사가 글로 남는지                                  |
| 무너진 구조         | h1이 하나인지, 제목 단계를 건너뛰지 않는지, 이름 없는 링크·버튼이 없는지 |
| 낮은 대비           | 모든 글자가 배경 기준 6:1을 넘는지                                       |

대비는 배경색 하나만 보고 재지 않는다. 이 지면의 유리와 젤은 반투명이라 그 아래
색까지 바깥에서 안쪽으로 차례로 섞어야 실제로 눈에 닿는 대비가 나온다. 섞지 않고
쟀더니 크림색 유리 위의 잉크가 2.9:1로 나왔다 — 실제로는 6.3:1이다.

가로 넘침은 «굴러가는가»가 아니라 «잘려 나가는가»로 본다. 이 지면은 `#root`에
`overflow-x: clip`을 두고 있어서 무엇이 얼마나 새든 스크롤은 생기지 않는다 —
그것을 «자르는 조상»으로 치면 검사가 아무것도 잡지 못한다. 실제로 그렇게 만들어
두고 2000px짜리 요소를 넣었더니 그대로 통과했다. 뿌리의 clip은 사고를 막아 주는
장치이지 사고가 없다는 증거가 아니다. 대신 색면과 젤은 일부러 판면보다 크게 잡혀
있으므로, 잃을 것이 있는 것 — 글자 · 그림 · 누를 것 — 만 사고로 센다.

## 배포

`main` 브랜치에 push하면 GitHub Actions가 포맷·린트·타입 검사를 먼저 돌리고,
통과한 경우에만 빌드해서 GitHub Pages로 배포한다. 검사가 실패하면 배포되지 않는다.
화면 검사는 브라우저를 띄워야 해서 CI에 넣지 않았다. 화면에 손을 댔으면
`npm run audit`을 직접 돌리고 나서 올린다.

MAMABOY의 피드 워크플로는 여섯 시간마다 따로 돈다. 봇이 만든 커밋은 push 이벤트를
일으키지 않으므로, 배포 워크플로가 그 워크플로의 완료를 직접 듣는다
(`workflow_run`). 번역까지 하려면 저장소 시크릿에 `ANTHROPIC_API_KEY`가 있어야 하고,
없으면 수집만 하고 원문 그대로 둔다.

## 남은 작업

- 제보 접수 창구: 현재 인스타그램 DM으로 연결된다. 전용 폼을 쓰려면
  `src/App.tsx`의 `REPORT_HREF` 값만 교체하면 된다.
- MAMABOY의 RSS 소스: 등록된 일곱 곳의 이용 조건을 2026-08-22에 한 번 확인했고,
  결과는 `sources.json`의 `note`에 매체별로 적혀 있다. 조건 없이 쓸 수 있는 것은
  **Fight Aging!(CC BY 4.0)** 하나뿐이다. Lab Muffin은 사전 허락이 필요하고,
  Nature Aging은 건별 유료 허가에다 피드가 0건이며, The Toy Book은 약관이 공개
  게시를 금지하고, It's Nice That은 피드가 404다. Lifespan.io는 조건을 확인하지
  못했다 — 모르는 것은 허락받은 것이 아니다.

  그래서 아직 전부 `enabled: false`다. Fight Aging! 하나만 켜서 실제로 돌려 봤더니
  8건이 전부 AGE 한 카테고리였다. 조건이 맞는 매체가 한 곳뿐이면 이곳은 매거진이
  아니라 장수 연구 뉴스레터가 된다. CURIOSITY 쪽에 쓸 수 있는 매체가 생기는 날
  함께 켠다. The Public Domain Review는 CC BY-SA라 조건은 맞지만 받아 온 6건이
  전부 편집 기준에서 떨어졌다 — 이곳의 CULTURE는 «지금 생겨나는 취향»이고 그
  매체는 퍼블릭 도메인 미술사다. 조건이 맞는 것과 지면에 맞는 것은 다른 문제다.

- MAMABOY의 번역: `AZURE_TRANSLATOR_KEY`가 저장소 시크릿에 없다. 없어도 수집은
  끝나지만 모든 기사가 `translationStatus: 'pending'`으로 남아 원문 제목 그대로
  걸린다. Azure Translator의 무료 티어(F0)는 달마다 200만 자이고 이 지면이 쓰는
  양은 그 절반이 안 된다 — 키만 넣으면 비용 없이 번역이 돈다.
- MAMABOY의 검색: 지금은 모든 기사가 클라이언트에 있으므로 `services/search.ts`가
  직접 훑는다. 누적된 기사가 수백 건을 넘으면 색인을 미리 만들어 두는 쪽으로 바꾼다.
- SEMICOLON의 두 번째 SESSION: 첫 기록(`wellknews-1k`)은 `display: 'stage'`로
  만들었지만, 다음 기록부터는 기본값인 `column`으로 쓰는 것이 맞다. 판면을 통째로
  가져가는 형태가 표준이 되면 그 순간 특별할 것이 없어진다.
