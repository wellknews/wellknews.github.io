# v1.4.0 — 중간값은 올리브였다

에카타 개편에서 나온 이야기를 SEMICOLON에 두 편으로 나누어 남긴다. 한 편은
이어지는 중인 생각이라 THREAD로, 한 편은 두 해시가 경계를 정하는 기록이라
CODE로 갔다. 한 편에 넣으면 둘 중 하나가 다른 하나의 각주가 된다.

## CODE — 「중간값은 올리브였다」

`/;/code/the-middle-was-olive` · `wellknews.github.io` `efc4745 → f1dc1ed`

축은 「무엇이 좋아졌는가」가 아니라 **「무엇을 잘못 짚었는가」**다. 좋아진 것은
`docs/releases/v1.3.0.md`가 이미 더 정확하게 갖고 있고, 같은 글이 두 곳에 서면
둘 중 하나는 반드시 뒤처진다. 여기 남긴 것은 그 노트에도 커밋 로그에도 없는
쪽이다 — 섞으려는 시도가 있었다는 것, 회색이 타협이었다는 것, 확인하던 틀
안에서는 무너진 자리가 보이지 않았다는 것.

| 장치    | 무엇을 말하는가                                                                                       |
| ------- | ----------------------------------------------------------------------------------------------------- |
| `Miss`  | 겨눈 것 셋에 줄이 그어지고, 목록 **바깥**에 「면적」이 앉는다. 겨눈 적이 없어서 빗나갈 수도 없었던 것 |
| `Gate`  | 다섯 관문이 전부 통과선을 끝까지 긋고, 「넘치는지 보는 자리」에는 아무것도 그리지 않는다              |
| `Delta` | 두 줄. 아래 줄의 막대 두 개가 **같은 길이**다                                                         |
| `Open`  | 못 잰 넷. 마지막이 그대로 닫는 문장으로 이어진다                                                      |

`Delta`의 두 번째 줄이 이 기록의 핵심이다. 보이는 방식을 전부 바꾸는 동안
카드가 읽는 필드는 하나도 늘지 않았고 하나도 줄지 않았다. 한 줄만 실으면
개선 보고서가 되고, 두 줄을 나란히 놓아야 「정리한 것이 아니라 다른 면적에
나눠 놓은 것」이 보인다.

## THREAD — 「섞을 수 없는 두 색을 나란히 두는 법」

`/;/thread/burgundy-and-neon`

형광 라임과 버건디 사이에서 중간을 찾으려 한 이야기. 채도 63과 100, 명도 20과
64 사이의 중간은 올리브이고 올리브는 어느 쪽도 아니다. 이 문제를 가장 정직하게
푼 쪽은 인쇄기였다 — 리소그래프는 드럼이 색마다 따로라 애초에 섞을 수가 없고,
그래서 한 장에 두 번 찍는다. 두 색을 받아 주는 것은 색이 아니라 종이다.

## 쓰면서 고친 것 셋

**필드 수가 13이 아니라 14다.** 요청서가 `item.status`를 목록에서 빠뜨렸다. 두
판본에서 직접 세었고 집합이 완전히 같다. 세는 명령을 기록의 주석에 적어 두었다.

**`Delta`가 변화 없는 줄에 `−0%`를 찍고 있었다.** 0에 `−`를 붙이면 「아주 조금
줄었다」로 읽힌다. 이 장치에서 「그대로」는 결과가 없는 것이 아니라 결과이고,
이번 기록이 정확히 그 경우라 첫 번째로 밟았다.

**확인되지 않는 문단을 THREAD에서 뺐다.** 나이키 볼트는 형광 신발이 2012년
런던에서 널리 신긴 것까지가 사실이고, 이유는 자료가 「황록에 대한 눈의 민감도와
붉은 트랙의 대비」 및 스폰서 규정을 말한다 — 글이 적은 「면적 원리」가 아니다.
비즈니스위크 쪽의 「형광이 면이 된 적 없다」도 확인되지 않는다. 공개되는 지면
이므로 뺐고, 뼈대인 리소그래프와 하이비스는 그대로 선다.

## 이 게시판이 앞으로 따를 기준

`commits`는 병합을 빼고 센다. 표지의 막대가 diffstat을 `commits`만큼의 칸으로
자르고, 그 칸이 뜻하는 것은 「이 변경이 몇 번에 나뉘어 도착했는가」다. 병합은
도착한 것이 아니라 합쳐진 자리라 칸을 하나 늘리면서 아무것도 싣지 않는다.

## 그 밖에

- 새 기록을 `npm run audit`의 검사 대상에 넣었다. 넣지 않으면 그 글만 검사
  밖에 남는다.
- 브랜치 정리 워크플로가 생겼다(`Prune merged branches`). 지울 목록을 적어
  넣지 않고 러너가 매번 「이 브랜치의 커밋이 전부 main에 있는가」를 다시 센다.
  실수로 돌려도 작업 중인 브랜치를 지울 수 없다.
- 검사가 멀쩡한 장치를 죽었다고 하던 세 가지를 고쳤다. 계단으로 움직이는 점을
  한 순간만 훔쳐보던 것, 「변환이 걸렸는가」와 「점이 옮겨 갔는가」를 구분하지
  않던 것, 그리고 고정 헤더가 덮은 자리로 커서를 보내던 것. 마지막 것은
  이 릴리스에서 코드 목록이 길어지자마자 드러났다. 이제 실패할 때 커서 아래에
  무엇이 있었는지를 함께 적는다 — 「반응하지 않는다」만 있으면 그 다음에 할 일이
  손으로 다시 재 보는 것뿐이고, 손으로 재면 대개 멀쩡하다.
