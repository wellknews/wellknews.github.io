## 00. 왜 한 편이 아니라 두 편인가

이 작업에서 나온 이야기는 두 종류였고, 이 공간에는 그 둘을 받는 게시판이
따로 있다.

| 무엇                                                  | 어디   | 왜                                                                                         |
| ----------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------ |
| 형광과 심색을 섞으려다 못 섞은 이야기. 찾아본 사례들. | THREAD | 해시가 없다. 이어지고 있는 생각이고, 「완성된 분석이 아니어도 된다」가 그 게시판의 전제다. |
| 그 결론이 어느 커밋에서 어떻게 구현되었는가.          | CODE   | 경계를 두 개의 해시가 정한다. 지어낼 수 있는 값이 거의 없다.                               |

한 편에 넣으면 둘 중 하나가 다른 하나의 각주가 된다. 사례 모음이 커밋
기록의 서론이 되거나, 커밋 숫자가 메모의 근거로 끌려 들어가거나.

**THREAD — 작성 완료.** `burgundy-and-neon` · 2026-09-06 ·
「섞을 수 없는 두 색을 나란히 두는 법」. 리소그래프 · 비즈니스위크 · 나이키
볼트 · 하이비스 안전색에서 시작해, 96대 1이라는 우리 숫자와 「이건 섞은 것이
아니라 나란히 둔 것」이라는 열린 끝맺음까지 간다. `form: 'note'`, 소제목 없음,
장치 없음 — 그 게시판의 일곱 편이 전부 그렇게 서 있다.

> **확인이 필요한 것.** 리소그래프의 드럼 구조와 하이비스 안전색 규격은
> 사실이지만, 비즈니스위크(리처드 털리 시절)와 나이키 볼트(2012)는 기억에서
> 꺼낸 것이다. 공개되는 지면이므로 **올리기 전에 한 번 확인한다.** 확인이
> 어려우면 두 문장을 빼도 글은 선다 — 이 메모의 뼈대는 리소그래프와
> 하이비스이고, 나머지 둘은 같은 원리의 예시다.

아래는 **CODE 쪽** 요청이다.

## 0. 요청 한 줄

에카타 Story 미리보기를 웰뉴스 계정의 문법으로 다시 세운 작업을 CODE 기록
한 편으로 남긴다. **릴리스 노트를 옮겨 적는 것이 아니다.**

결론 세 줄.

1. 이 기록의 축은 「무엇이 좋아졌는가」가 아니라 **「무엇을 잘못 짚었는가」**다.
   좋아진 것은 `docs/releases/v1.3.0.md`가 이미 더 정확하게 갖고 있다.
2. 잘못 짚은 것은 **두 색 사이에서 중간을 찾으려 한 것**이다. 중간은 없었고,
   첫 판에서 나온 것은 중간이 아니라 회색이었다 — 결정을 미룬 자리.
3. 그리고 톤을 맞추러 갔다가 **조판이 실측 폭에서 넘치는 것**을 찾았다.
   다섯 관문이 전부 통과인 채로 세 건이 검수 보류로 넘어가고 있었다.

## 2. 지어내면 안 되는 값

게시판의 첫 규칙이다. 아래는 전부 git이 세어 준 값이고, 명령을 함께 적어
두었으니 의심스러우면 다시 돌린다.

```
repo:     'wellknews.github.io'
revision: { from: 'efc4745', to: 'f1dc1ed' }
diff:     { commits: 3, added: 578, removed: 146 }
meta:     { date: '2026-09-06', type: 'DESIGN' }
```

```sh
git rev-list --count efc4745..f1dc1ed      # 3
git diff --shortstat efc4745 f1dc1ed       # 7 files, 578 insertions(+), 146 deletions(-)
```

`commits: 3`은 병합 커밋을 포함한 값이다. 작업 커밋만 세면 2이고
(`--no-merges`), 어느 쪽을 쓰든 **본문에 그 수를 다시 적지 않는다** — 막대의
눈금이 이미 말한다.

`type`은 자유 문자열이다. `'DESIGN'`을 제안한다. 이 작업은 성능이 아니고,
두 브랜드가 한 면에서 만나는 문제였으므로 `'BRAND'`도 후보다. 하나만 고른다.

**slug·제목·excerpt 제안** (쓰는 사람이 바꿔도 된다)

```
slug:    'the-middle-was-olive'
title:   '중간값은 올리브였다'
excerpt: '두 색 사이에서 중간을 찾으려 했다. 첫 판에서 나온 것은 중간이 아니라 회색이었다.'
```

다른 후보: 「섞을 수 없는 것을 나란히 두는 법」 · 「색을 바꾸러 갔다가 7px을
찾았다」. 앞의 것은 결론이라 기록의 축이 되기 어렵고, 뒤의 것은 축이 조판으로
옮겨 간다. 축은 하나여야 하고, 조판 쪽은 §4.2가 받는다.

## 3. 왜 릴리스 노트를 옮겨 적으면 안 되는가

`v1.3.0`은 이미 잘 쓰인 노트다. 여섯 줄 대조표가 있고, 색상각·채도·명도가
있고, 리소 인쇄와 면적비 96대 1이 있다. 그것을 CODE로 옮기면 같은 글이 두 곳에
서게 되고, 둘 중 하나는 반드시 뒤처진다.

노트에 **없는** 것을 쓴다.

- 노트는 「섞지 않는다」는 **결론**을 적었다. 그 결론에 닿기 전에 **섞으려는
  시도가 있었다**는 사실은 어디에도 없다.
- 노트는 우상단이 `EKATA ▪`라고 적었다. 그 자리가 처음에는 회색
  `AN EKATA CAMPAIGN`이었고, **회색이 타협이었다**는 것은 적혀 있지 않다.
- 노트는 격자를 고쳤다고 적었다. 그 버그가 **480px 미리보기에서는 보이지
  않았다**는 것, 그러니까 확인하던 틀 안에서는 없어진 것이 보이지 않았다는
  것은 적혀 있지 않다.

세 가지 모두 커밋 로그에도 없다. CODE가 받아야 할 것이 그쪽이다.

## 4. 넘기는 재료

사실만 적는다. 문장은 쓰는 사람이 짠다.

### 4.1 겨눈 곳과 실제로 있던 곳 — `Miss`

겨눈 것 셋. 전부 빗나갔다.

| 겨눈 곳                        | 왜 빗나갔는지                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 「색을 바꾸면 된다」           | 계정과 대조해 보니 어긋난 것이 여섯 줄이었고 색은 그중 한 줄이었다. 바탕·분야 표시·발행 표시·서명·조판 무게가 전부 달랐다. |
| 「두 색의 중간을 찾으면 된다」 | 채도 63과 100, 명도 20과 64 사이의 중간은 올리브다. 올리브는 어느 쪽도 아니고, 중간을 취하는 순간 둘 다 죽는다.            |
| 「회색이면 둘 다 안 건드린다」 | 실제로 첫 판이 회색 `AN EKATA CAMPAIGN`이었다. 에카타가 있기는 한데 색이 없어서 **에카타로 읽히지도 사라지지도 않았다.**   |

실제로 거기 있던 것 (겨눈 적이 없어서 빗나갈 수도 없었던 것):

> **면적.** 문제는 어떤 색을 쓰느냐가 아니라 그 색이 몇 퍼센트를 덮느냐였다.
> 발행 칩 0.47%, 캠페인 램프 0.005%. 96대 1에서 두 색은 싸우지 않는다.

`Miss`는 겨눈 항목에 줄을 긋되 글자는 그대로 읽히게 하고, 마지막 항목은
목록 바깥에 앉힌다. 위 표가 그 구조 그대로다.

### 4.2 관문 — `Gate`

통과한 것 (`passed`). 실제로 돌린 명령을 그대로 적는다.

| 명령                                       | 세어 준 것 |
| ------------------------------------------ | ---------- |
| `npm run format:check`                     | prettier   |
| `npm run lint`                             | oxlint     |
| `npm run typecheck`                        | tsc -b     |
| `npm run build`                            | vite       |
| `node --test scripts/ekata-check.test.mjs` | 4 tests    |

관문이 없는 자리 (`absent`):

> 실측 폭에서 조판이 넘치는지 보는 관문.

그 자리에서 무너진 것 (`fell`):

- 1080px에서 `.story-facts`가 305px 칸에 312px을 넣었다. 모자란 것은 **7px**.
- 홍길동·이하늘·박지우 — 가장 짧은 사건 셋이 검수 보류 화면으로 넘어갔다.
- 480px 미리보기에서는 다섯 건 모두 정상으로 보였다. 컨테이너 쿼리는 배율을
  따라가지만 줄바꿈은 따라가지 않는다.

이 장치의 취지가 정확히 여기다 — 전부 통과했는데도 무너졌고, 무너진 자리에는
애초에 관문이 없었다.

### 4.3 잰 것 — `Delta`

두 줄을 **반드시 나란히** 놓는다. 하나만 쓰면 개선 보고서가 된다.

| 잰 것                           | 전  | 후  | 단위 |
| ------------------------------- | --- | --- | ---- |
| 실측 폭에서 한 장에 들어간 사건 | 2   | 5   | 건   |
| 카드가 읽는 사건 필드           | 13  | 13  | 개   |

두 번째 줄의 막대 두 개는 길이가 같다. 그것이 이 작업의 핵심 사실이다 —
**보이는 방식을 전부 바꾸는 동안 정보는 한 개도 늘거나 줄지 않았다.** 이 줄이
없으면 「정보를 정리했다」로 읽힐 자리가 남는다.

13개 필드: `photoUrl` `name` `ageAtMissing` `currentAge` `sex` `missingDate`
`missingArea` `height` `weight` `physicalFeatures` `clothing` `sourceLabel`
`verifiedAt`. 앞뒤가 같다는 것은 이렇게 확인했다.

```sh
for rev in efc4745 f1dc1ed; do
  git show $rev:src/ekata/components/EkataStoryCard.tsx | grep -o "item\.[a-zA-Z]*" | sort -u
done
```

### 4.4 못 쟀거나 하지 않은 것 — `Open`

성과 뒤의 각주로 몰지 않는다. 잰 것과 같은 판면에 둔다.

| 무엇                               | 왜                                                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 실제 공개 사진으로 확인하지 못했다 | 다섯 건 모두 가상 데이터라 사진이 없다. `contain`이 세로 증명사진을 어떻게 앉히는지는 실물이 와야 안다.      |
| 앱이 굽는 그림과 겹쳐 보지 못했다  | 값은 카드 포지 소스에서 옮겨 왔지만, 실제로 구운 PNG와 픽셀로 대조한 것은 아니다.                            |
| 글꼴이 다르다                      | 앱은 SUIT ExtraBold·IBM Plex Sans KR Bold, 웹은 Pretendard 800이다. 미리보기는 근사값이다.                   |
| 팔로워에게 물어보지 않았다         | 「갑작스럽지 않은가」는 결국 사람이 답할 질문이다. 이 작업이 한 것은 그 답이 아니라 **답할 수 있는 형태**다. |

### 4.5 닫는 자리 — `Quiet`

숫자가 없는 유일한 대목이다. 마지막 항목(§4.4의 넷째)이 그대로 이 자리로
이어진다. 연출을 더하는 대신 빼는 자리다.

## 6. 쓰지 않는 것

- **소제목(h3).** 이 공간의 어느 기록도 쓰지 않는다. 구간을 나누는 것은
  여백이고, 이름을 붙일 자리에는 `Passage tone="loud"` 한 문장을 놓는다.
- **`Prompt`.** 이 작업에는 지운 창이 없다. 「답이 하나뿐인 물음」을 색 결정에
  갖다 붙이면 장치의 은유가 무너진다. 억지로 쓰지 않는다.
- **새 조판 장치.** 만들기 전에 묻는다 — 이것이 문장을 대신하는가, 아니면
  문장 옆에 그림을 하나 더 두는 것인가. 이 기록에는 뒤쪽밖에 없다.
- **`compact`.** 첫 기록도 두지 않았다. 필요해지면 그때 더한다.
- **면적비·색상각 표를 그대로 옮기는 것.** 그 표는 릴리스 노트의 것이다.
  여기에는 「0.47% 대 0.005%」 한 줄이면 족하고, 그것도 `Miss`의 마지막
  항목 안에서 말한다.
- **`Stat`을 body에 넣는 것.** 머리의 표지 자리에 자동으로 앉는다.

4. THREAD의 두 사례(비즈니스위크·나이키)를 확인해서 남길지, 뺄지. §00 참고.

   언급할지. 언급하면 이야기가 두 저장소로 벌어지고, 빼면 「그래서 실제
   게시는?」이 열린 채로 남는다. **빼는 쪽을 제안한다** — 그 질문은 §4.4의
